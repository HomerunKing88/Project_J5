# 설계 결정 기록

버전 1.2 / 2026-09-22. 아래 결정은 신규 구현의 기준이다. 소프트웨어 동작에 관한 사실은 말미 공식 근거와 구분한다. 공수·운영 절차·범위는 이 프로젝트의 설계 결정이다.

## ADR-01. 기본 스택 유지, 최초 기능 축소

결정: 정적 웹앱 + IndexedDB + PC SQLite + Python을 유지한다. 데이터는 Git 밖에 둔다. 클라우드 DB·실시간 동기화·가계자산 대시보드는 초기 제외한다.

v1.0의 문제는 정적 구성 자체보다 첫 릴리스에 넓은 변경 교환 기능을 포함한 점이다. R1a에서 수집·내보내기, R1b에서 정본·복구를 구현한다. 20개 표본의 완전한 자료 매칭과 모든 API 승인을 첫 임장 전제조건으로 두지 않는다.

화면은 HTML/CSS/ES Modules, 지도는 검증한 고정 MapLibre 배포본(ADR-12에서 자체 SVG 점 지도로 대체, 타일 이용조건 확인 후 재검토), ZIP 처리는 고정 fflate 배포본(ADR-11에서 자체 STORED 작성기로 대체), PC는 지원 중인 Python 버전과 표준 라이브러리를 우선한다. JSON Schema 검증과 사진 정규화에 필요한 의존성은 해당 단계에서 고정한다. PostGIS는 도입하지 않는다. 공간 전처리는 R2 이후 Shapely·pyproj를 실제 자료에 필요한 경우만 사용한다.

정적 호스팅은 코드 전용 HTTPS 배포로 유지한다. 공급자는 계정 확인 후 확정하며 전용 서버 API를 앱에 결합하지 않는다. 외부 타일·글꼴·사진의 숨은 통신을 기본값으로 추가하지 않는다. 서비스 워커에는 앱 실행 파일만 캐시한다. 개인 자료는 사용자가 불러온 파일과 IndexedDB로 관리한다.

## ADR-02. 신규 관측의 단방향 반영

결정: 스마트폰은 신규 관측을 작성하고, 한 PC가 정본을 반영·검토한다. 기존 사실의 수정·거래 연결·관심 단계 변경은 초기 모바일 교환 범위에서 제외한다.

휴대폰 한 대라는 조건만으로 중복·손상·수정 파일이 없어지는 것은 아니다. 내보낸 관측을 변경 불가로 고정하고 정정은 새 이벤트로 추가하여 기존 값 충돌의 발생 경로를 줄인다.

R1 필수: 이벤트 UUID, study_id, 형식 버전, 고정 이벤트 내용, 첨부 해시, 중복 확인, 형식·크기 검사, 정본 반영의 원자성, 별도 사본. 제외: 기준 데이터 버전 비교, 이벤트별 승인안 파일, 반영확인서 파일, 다기기 병합, 변경 충돌 해결 UI.

사용자 상태는 폰의 `저장됨 / 내보냄`, PC의 `반영됨`으로 단순화한다. `내보냄`은 사용자가 실제 파일 저장을 확인한 상태다. 폰에서는 PC 반영 상태를 자동 확인하지 않는다. 화면에는 필요한 경우 `PC 반영 여부 미확인`을 함께 표시한다. 자동 정리는 제공하지 않는다.

복수 기기에서 같은 값을 수정하는 테스트는 현 범위에서 제외한다. 같은 ID·다른 내용, 중복 수입, 첨부 누락, 저장공간 부족, 반영 중 장애 테스트는 유지한다. 이후 동기화 기능은 실제 불편을 확인한 새 ADR이 있을 때만 개발한다.

## ADR-03. 파생본은 전량 재생성하고 검증 후 게시

결정: 정본 반영 성공 후 지도·검색용 파생본을 전체 재생성한다. 재생성 실패는 정본 반영 실패와 구분한다. 이전 정상 파생본을 유지하고 정본·파생본의 버전 차이를 표시한다.

R1b는 정본에서 조회 ZIP을 생성하는 것으로 시작한다. R2 이후 필요할 때 물리적 읽기 테이블을 추가한다. 별도 읽기 테이블이 없더라도 파생 패키지의 생성·실패·버전 규칙은 적용한다.

한 번의 사용자 승인 배치를 하나의 재생성 단위로 한다. API의 각 행마다 재생성하지 않는다. 전체 재생성 비용은 먼저 측정하며, 부분 갱신은 측정 근거와 별도 결정이 있을 때만 도입한다.

게시 규약은 데이터 사전 §4에 둔다. SQLite 트랜잭션과 파일 교체는 각각의 원자성 경계를 가진다. DB와 여러 파일이 하나의 분산 트랜잭션으로 함께 커밋된다고 가정하지 않는다. [E04][E05]

## ADR-04. 조사 경로와 통계 표본틀 분리

결정: `survey_route`, 경로 버전, 물리적 점포, 표본틀 버전, 조사 실행, 점포 관측을 구분한다.

같은 경로를 걸어도 점포 분할·통합·용도변경·조사 누락으로 분모가 바뀔 수 있다. 공실률의 분모는 해당 조사 표본틀과 확인된 상태에서 계산한다. 경로의 순서는 반복 관측의 재현성을 돕는 정보다.

R1a부터 경로 버전 ID를 선택 입력할 수 있게 한다. 첫 고정 경로와 점포 목록은 작은 수동 파일로 관리한다. 자유 임장은 경로 없이도 저장한다. R2에서 표본틀 버전·조사 세션·미조사 점포·공통 표본 비교를 구현한다. 경로 편집기와 자동 길찾기는 제외한다.

## ADR-05. 거래 소급 범위 확대, 현재 비교는 분리

결정: 최초 소급 목표를 2006-01로 확대한다. 최근 약 5년 수집·검토부터 활용하고, 2011년 이후와 2006~2010년 자료를 이어 수집한다. 옛 자료 수집 완료가 임장이나 최근 거래 사용을 막지 않는다.

공식 공개안내는 상업·업무용 등을 2006년 1월 이후 신고자료의 공개 대상으로 설명한다. 다만 현재 상업업무용 API의 시기별 완전성과 각 필드 제공 여부는 인증 호출로 확인해야 한다. 공개 대상 시작일만으로 전 기간 완전 수집을 선언하지 않는다. [E01][E02]

요청 단위는 API 명세에 맞춘 시군구 코드·계약월·페이지다. 같은 구 안의 여러 비교 블록을 이유로 동일 요청을 반복하지 않는다. 최초 수집, 최근 기간 재조회, 누적 자료 정정 점검을 구분한다.

R0 통과조건의 표본 월 3개 실측 결과로 R3의 범위와 공수를 조정한다. 핵심 범위와 비교 블록을 합친 연결 검토 대상이 연 30건 내외로 낮으면 연결 검토 화면은 구현하지 않고 CSV 목록과 수동 확인으로 대체한다. 실측 항목은 릴리스 계획 §4를 따른다.

장기 공개 거래는 다른 이용자도 확보할 수 있다. 프로젝트 고유 기록은 검증한 물건 연결, 임장·사진·임대 변화와 당시 투자판단이다. 과거 거래를 현재 비교가격으로 일괄 환산하거나 최근 거래와 같은 평균에 넣지 않는다.

## ADR-06. 비교 블록은 단계적으로 상세화

결정: 핵심 범위는 확보 가능한 필지·건물 기초정보를 관리하되 정기 관찰은 30~50개 이내의 운영 목표로 시작한다. 배경 자료에 정기 임장 의무를 부여하지 않는다.

비교 범위는 거래 원본·정규화와 출처·시점을 우선한다. 거래가 특정 PNU로 검증되었거나 비교 대상으로 지정된 물건에 공시지가·필지·건축물·규제 정보를 추가한다. 주소 미확인 거래에 공시지가를 추정 연결하지 않는다. [E02]

API가 구 전체 응답을 반환하면 원본은 수집 범위대로 보존하고 앱 조회 범위만 필터한다. 과거 전체 자료를 모바일 패키지에 모두 넣지 않는다. v1.0의 3,000필지는 성능 시험값으로 유지하며 데이터 보관 상한이나 전수 조사 목표로 사용하지 않는다.

## ADR-07. 매입 준비를 별도 검토 상태로 정의

결정: R7에 매입 검토 기능을 둔다. R2부터 해당 기록 형식의 수동 체크리스트를 사용할 수 있다. 매입 기회가 빨리 생기면 R7을 앞당길 수 있으며 2035년까지 기능 구현을 미루지 않는다.

`purchase_ready`는 이 도구에서 계약 협상에 필요한 검토가 유효하게 준비된 상태를 뜻한다. 자동 매수 지시, 대출 확약, 허가 또는 계약 적법성 보증을 뜻하지 않는다.

가격·범위·전략·금융조건·규제·임대차가 변하면 준비 상태를 재검토한다. 체크리스트·재검토 조건은 데이터 사전 §11에서 정의한다. 계약 직전과 잔금 직전 재확인은 별도로 둔다.

## ADR-08. 계산 입력을 먼저 정규화

결정: 매입 현금 계산의 가격 기준은 보증금 차감 전 계약 총액이다. 순액 입력은 근거가 있는 차감 항목으로 총액을 복원한다. 잔금만으로 총액을 복원하지 않는다.

면적은 공부면적, 법정 산정 대지면적, 건물 배치 검토영역을 분리한다. 도로 확폭·건축선·시설 편입 등의 사유를 기록하고 법정 분모에서 제외할지는 확인 결과로 정한다. 모든 후퇴면적을 자동 차감하지 않는다. [E03]

v1.0의 용적률 산정용 연면적, 승계 보증금 반환 의무, 사업기간 최대 필요자기자본 구분은 유지한다. 식과 가상 검증 사례는 데이터 사전 §9~10에만 둔다.

## ADR-09. subjects 유지 및 참조 무결성 보강

결정: 공통 `subjects`는 유지한다. 각 기록에 `subject_type + subject_id`만 넣고 공통 부모를 없애는 변경은 채택하지 않는다.

공통 부모를 없애면 대상 존재 여부를 일반 외래키 하나로 검증하기 어렵다. 타입이 다른 대상 테이블의 선택·삭제 검사를 애플리케이션에 반복 구현하는 부담이 생긴다. SQLite는 고정된 부모 키에 대한 외래키와 복합 외래키를 지원한다. [E06]

`subjects(subject_id, subject_type)`에 UNIQUE를 두고, 하위 테이블은 고정 타입 CHECK와 복합 FK를 사용한다. records의 대상 존재는 FK로 확인한다. `record_type`과 허용 대상 타입의 의미적 조합은 공통 검증 함수와 테스트 한 곳에서 관리한다. 모든 연결의 외래키 활성화는 필수다.

관찰 경로·세션 등 독립 객체를 모두 subjects에 넣지 않는다. 실제로 공통 관측·근거를 연결해야 하는 필지·건물·매입 단위·점포부터 필요 시 생성한다. R1a의 파일 기록은 해당 ID를 보존하고 R1b에서 정본 관계를 검증한다.

## ADR-10. 공수와 문서 유지 방식

결정: v1.0의 108~164시간 추정을 신규 일정에 사용하지 않는다. 클로드의 60~90시간·전체 300시간도 실측값으로 취급하지 않는다. 축소한 작업을 다시 분해하고 완료 PR의 실측으로 잔여 추정을 갱신한다.

첫 임장 수집 시험은 R1a, 안정적 정본 운영은 R1b다. 둘의 완료를 같은 시점으로 약속하지 않는다. API 승인·전문가 검토·실제 자료 정리·정기 임장은 개발 순작업 시간과 구분한다.

활성 문서는 AGENTS 1개와 본문 3개다. README는 길찾기와 변경 요약만 둔다. 자료형·필수값은 실행 스키마로 검증하고 설명을 문서 여러 곳에 복제하지 않는다.

## ADR-11. 관측 패키지 ZIP은 자체 STORED 작성기로 만든다

결정: 폰 앱의 `.j5field.zip` 생성은 외부 라이브러리(ADR-01의 fflate) 대신 저장소 안의 순수 JS STORED 전용 작성기(`web/app/zip.js`)로 한다. 2026-09-22 J5-007에서 채택.

근거: 패키지 내용의 대부분은 JPEG/PNG/WebP 사진이라 DEFLATE 이득이 거의 없다. 외부 코드를 고정 배포본으로 넣으면 공급망·라이선스·해시 관리와 갱신 검증이 계속 필요하다. STORED 전용 작성기는 약 150줄이고, Python `zipfile`(testzip·CRC·이름·시각)과 `j5 inspect`를 오라클로 테스트한다. 데이터 디스크립터·ZIP64·암호화는 만들지 않으며 PC 검사기가 허용하는 STORED/DEFLATED 중 STORED만 낸다.

대안: fflate 고정 배포본. 압축이 필요해지거나(예: 텍스트 위주 패키지) 4GB 초과가 필요해지면 다시 검토한다. ADR-01의 "ZIP 처리는 고정 fflate 배포본" 문구는 이 결정으로 대체한다.

## ADR-12. 최소 지도는 자체 SVG 점 지도로 그린다

결정: R1a의 지도는 외부 라이브러리(ADR-01의 MapLibre) 대신 저장소 안의 순수 JS Web Mercator 투영 + SVG 점·라벨(`web/app/map.js`)로 그린다. 배경 타일·외부 통신은 없다. 목록이 주 화면이고 지도는 보조 화면이며, 지도 생성·갱신이 실패하면 안내만 남기고 목록·기록·내보내기는 그대로 동작한다. 2026-09-22 J5-005에서 채택.

근거: 이용조건을 확인한 타일 출처가 아직 없어 어떤 렌더러를 쓰든 빈 배경에 위치점만 그린다. MapLibre 고정 배포본(6.x, ESM 전용 약 1.2MB)은 XMLHttpRequest·innerHTML·워커 eval·blob 워커를 포함해 정적 보안 테스트(외부 URL·네트워크 API·HTML 문자열 삽입 금지) 예외와 CSP 완화(worker-src), 공급망·라이선스·해시 관리를 요구한다. 점 지도는 약 220줄이고 투영·맞춤·확대 수학은 Node 단위 테스트, 화면·탭·실패 경로는 헤드리스 Chromium e2e로 검증한다.

대안: MapLibre 고정 배포본 + 타일. 타일 출처와 이용조건(AGENTS 구성 절)이 확정되면 새 ADR로 검토하며, 그때 WebGL 실패 시 목록 fallback과 vendor 해시 검증 테스트를 함께 둔다. ADR-01의 "지도는 검증한 고정 MapLibre 배포본" 문구는 그때까지 이 결정으로 대체한다.

## ADR-13. 필지 경계·지번은 연속지적도 변환 번들을 폰에 파일로 넣어 SVG 로 그린다

결정: 지도에 필지 구분과 지번을 표시하기 위해 배경 타일 대신 연속지적도(공공 자료) 폴리곤을 쓴다. PC 도구 `j5 parcels convert` 가 사용자가 받은 연속지적도 SHP 를 조사 범위로 잘라 WGS84 GeoJSON 번들(`.j5parcels.json`, `schemas/parcels_bundle.schema.json`)로 만들고, 폰 앱은 시드처럼 그 파일을 불러와 IndexedDB 에 두고 자체 SVG 지도(ADR-12)의 점 아래 층에 경계·지번 라벨을 그린다. 필지 탭은 지번·PNU·도형면적과 그 안의 위치점 물건을 보여 주고 관측 기록으로 잇는다. 외부 통신은 여전히 없다. 2026-09-23 J5-013B-1 에서 채택.

근거: 사용자가 지도에서 필지를 구분해 필지별 자료를 넣으려면 경계와 지번이 필수인데, 이용조건을 확인한 타일이 없고 온라인 지적 레이어(VWorld 등)는 ADR-01 의 "숨은 통신 없음"·오프라인 사용과 맞지 않는다. 연속지적도는 공공누리 조건을 확인해 쓰는 파일 자료라 폰에 한 번 넣으면 오프라인에서 쓸 수 있고, 조사 범위 수천 필지는 SVG path 로 감당된다(범위 자르기·상한 8,000·경로는 로컬 단위로 한 번만 만들고 이동·확대는 그룹 transform). 좌표계 변환(횡축 메르카토르 역변환·Korean 1985 데이텀 변환)은 표준 라이브러리로 구현하고 pyproj 계산값과 mm 이내로 대조해 두었다(테스트 상수). ADR-01 의 "R2 이후 Shapely·pyproj 는 실제 자료에 필요한 경우만" 은 유지하며 지금은 필요하지 않다.

경계: 번들은 파생 조회자료이며 정본이 아니다. 정본 `parcels` 테이블·`asset_components`(데이터 사전 §2·§6)와 PNU↔asset_id 연결은 J5-013B-2 에서 PC 명령(`parcels-load`·`parcels-suggest`·`parcels-link`)으로 하고, 파생본 `parcels.geojson` 이 연결 물건을 폰에 전달한다. 폰은 위치점 포함과 파생본의 연결을 보여 줄 뿐 PNU↔물건 연결을 편집하지 않는다. 실제 번들은 사용자의 조사 범위를 드러내므로 저장소·공개 배포에 넣지 않으며 공개 앱에는 가상 필지만 둔다. 도형면적은 공부면적과 구분한다. Bessel(Korean 1985) 자료는 공식 변환의 정확도가 수 m 급이라 위치점과 대조한다.

대안: (1) VWorld 타일·지적 WMS: 온라인 필수, 약관·키 관리, ADR-01/12 변경 필요. 오프라인 임장과 맞지 않아 보류. (2) MapLibre 벡터 렌더링: 데이터 준비 문제는 같고 ADR-12 의 공급망 비용이 더해진다. 타일 이용조건이 확정되면 그때 재검토.

## ADR-14. 표 정의를 바꾸는 마이그레이션은 외래키 검사를 끈 한 트랜잭션으로 재작성하고 검사 뒤 커밋한다

결정: `records.record_type` 처럼 표 정의(CHECK)에 박힌 허용 목록을 넓혀야 할 때는 SQLite 권장 절차대로 새 표를 만들고 복사한 뒤 옛 표를 지우고 이름을 바꾼다. 저장소의 마이그레이션 실행기는 이런 마이그레이션(`FK_OFF_MIGRATIONS`)만 외래키 검사를 끈 채 `BEGIN IMMEDIATE` 한 트랜잭션으로 실행하고, 커밋 전에 `PRAGMA foreign_key_check` 가 비어야 커밋하며, 끝나면 외래키를 다시 켜고 켜졌는지 확인한다. 나머지 마이그레이션은 외래키를 켠 채 각자 트랜잭션으로 실행한다. 기존 마이그레이션 문구는 고치지 않는다(마이그레이션 1 은 `RECORD_TYPES_V1` 로 고정). 2026-09-25 J5-015A 에서 채택. J5-016C(마이그레이션 12)에서 같은 절차를 다시 써 기록 종류를 넓혔고, 마이그레이션 9 의 허용 목록은 `RECORD_TYPES_V9` 로 고정했다. J5-018A(마이그레이션 13)에서 매입 준비 검토 종류를 더하며 마이그레이션 12 의 목록은 `RECORD_TYPES_V12` 로 고정했다.

근거: 외래키를 켠 채로는 옛 표 삭제가 자식 표의 참조 위반이 되고(암묵적 DELETE), 이름 바꾸기가 자식 표의 참조 문구를 임시 이름으로 고쳐 버린다. 외래키를 끄고 재작성한 뒤 전체 검사를 통과해야 커밋하므로 "모든 연결에서 외래키를 활성화한다" 는 규칙의 목적(참조 무결성)은 지켜진다. 마이그레이션 하나가 실패하면 되돌리고 외래키를 다시 켠다.

대안: (1) 새 기록 종류를 별도 표로 두기: 데이터 사전 §2 의 "records 는 종류별 전체 스냅샷" 과 어긋나고 불변·정정 규칙을 두 번 구현해야 한다. (2) CHECK 없이 트리거로 검사: 기존 표의 CHECK 는 어차피 지울 수 없다.

## ADR-15. 외부 지도는 사용자가 누르는 링크로만 열고, 배경 타일은 넣지 않는다

결정: 지도 화면의 선택 카드와 필지 패널에 "다른 지도에서 보기" 링크(Apple 지도·네이버 지도·카카오맵·Google 지도)를 둔다. 링크는 `web/app/extmap.js` 한 파일에서만 만들고, 좌표(소수 6자리)와 고정 문구 "선택 위치" 만 담는다. 물건 이름·지번·PNU·기록은 보내지 않는다. 앵커는 새 창·`noopener noreferrer`·`referrerpolicy=no-referrer` 로 열어 앱 주소와 창 참조를 넘기지 않는다. 앱은 링크를 누르기 전에는 아무것도 전송하지 않으며 CSP `default-src 'self'` 와 서비스 워커 캐시 정책은 그대로다. 정적 검사(`tests/test_web_static.py`)는 외부 URL 을 그 파일의 허용 호스트 4개로만 제한하고, 그 파일에 통신·이동·저장 API 가 없는지 검사한다. 2026-09-27 J5-021 에서 채택.

근거: 사용자는 토지이음처럼 배경 지도 위에서 주변을 확인하고 싶어 하지만, 배경 타일 연동(네이버·카카오·VWorld API)은 온라인 전용에 클라이언트 키 노출·약관·오프라인 캐시 금지가 따르고 ADR-01/12 의 "숨은 통신 없음" 과 충돌한다. 사용자가 직접 누르는 링크는 AGENTS.md 의 "기기 데이터의 외부 전송은 사용자 승인 후" 를 그 탭 자체로 만족하며, 전송 내용을 좌표로 한정해 조사 범위·기록이 새지 않게 한다. 우리 지도는 기록과 필지 확인에, 외부 지도는 주변 확인에 쓰는 분업이다.

경계: 형식은 Apple 지도만 공식 문서로 확인했고(2026-09-27), 네이버·카카오·Google 은 작업 환경에서 공식 문서 접근이 차단돼 미검증이다(링크 `title` 에 표시, 실기기에서 확인). 링크 형식이 틀려도 외부 서비스의 기본 화면이 열릴 뿐 앱 데이터에는 영향이 없다. 배경 도형(도로·건물 윤곽)은 ADR-16, 앱 안의 배경 타일은 사용자 결정에 따라 ADR-18 에서 채택했다(이 링크는 보조로 남는다).

대안: (1) 배경 타일 API 연동: 위 이유로 보류. (2) 앱 URL 스킴(`nmap://` 등): 앱이 없으면 아무 일도 없거나 오류가 뜨고 등록 이름이 필요해 https 링크로 통일했다.

## ADR-16. 배경 도로·건물은 공공 도형 자료를 필지처럼 파일로 넣어 오프라인으로 그린다

결정: 지도 배경(도로·건물 윤곽·도로명)은 배경 타일 대신 공공 도형 자료(도로명주소 전자지도의 건물·실폭도로·도로구간 등 사용자가 허가받아 받은 SHP)를 PC 도구 `j5 basemap convert` 로 조사 범위로 잘라 WGS84 GeoJSON 번들(`.j5basemap.json`, `schemas/basemap_bundle.schema.json`)로 만들고, 폰 앱은 필지 번들처럼 파일로 넣어 IndexedDB(`basemap` 스토어, DB v3)에 두고 자체 SVG 지도(ADR-12)의 필지 아래 층에 실폭도로 → 건물 → 도로 중심선 순으로 그린다. 도로명 라벨은 같은 이름 중 화면에서 가장 긴 선분 하나에 붙이고, 화면 길이가 짧으면 숨기며, 다른 이름끼리 라벨 사각형이 겹치면 긴 쪽만 남긴다. 배경은 탭 대상이 아니며 물건·필지·기록과 연결되지 않는다. 번들은 도형과 도로명만 담고 건물명·건물 관리번호·주소·층수·소유 정보는 담지 않는다. 외부 통신은 여전히 없다. 2026-09-27 J5-022 에서 채택.

근거: 사용자는 토지이음처럼 배경 지도 위에서 주변을 파악하고 싶어 하지만 배경 타일 API 는 온라인 전용·키 노출·오프라인 캐시 금지로 ADR-01/12 와 충돌한다(ADR-15). 공공 도형 자료는 파일이라 한 번 넣으면 오프라인 임장에서 쓸 수 있고, SHP 읽기·좌표계 변환·범위 자르기·번들 검증은 ADR-13 의 필지 변환기를 그대로 재사용한다(폴리라인 읽기만 더했다). 상호(POI)는 없지만 도로·건물 윤곽과 도로명만으로 현장 방향 잡기에는 충분하고, 상호는 ADR-15 의 외부 지도 링크로 본다. 번들 상한 20,000 도형은 스키마·폰 검증기의 계약이며 실제 폰 성능은 실기기 항목이다.

경계: 배경 번들은 파생 조회자료이며 정본이 아니다(정본 표에 넣지 않는다). 실제 번들과 원본 SHP 는 조사 범위를 드러내므로 저장소·공개 배포에 넣지 않고 공개 앱에는 가상 배경만 둔다. 자료 배포처의 이용허락·신청 절차는 사용자가 확인해 `--license` 로 기록한다(작업 환경에서 확인하지 못했다). 배경이 오래돼도 앱은 도형 기준일과 가져온 시각을 보여 줄 뿐 최신이라고 표시하지 않는다.

대안: (1) 배경 타일 API: ADR-15 참조, 보류. (2) 국토지리정보원 수치지도: 층이 많고 형식 변환 부담이 커서 도로명주소 전자지도(건물·도로 층이 분리돼 있음)를 우선 대상으로 두고, 다른 자료도 같은 SHP 층 형식이면 그대로 쓴다.

## ADR-17. 폰은 조회 파생본 ZIP 을 직접 읽어 표시만 하고, 최신 여부는 파일만으로 단정하지 않는다

결정: 폰 앱은 PC 의 `j5 db project-copy` 가 만든 `.j5view.zip` 을 설정의 자료 관리에서 한 번에 읽어 물건 목록(`assets.seed.json`)·필지(`parcels.geojson`)·정본 기록(`records.jsonl`)·거래(`transactions.json`)를 넣는다(J5-011 이 미뤄 둔 항목). ZIP 읽기(`web/app/unzip.js`)는 PC 검사기와 같은 규칙(허용 이름 목록, 경로 탈출·절대경로·백슬래시·제어문자·암호화·심볼릭 링크·중복 거절, 항목 수·선언 크기·실제 바이트 한도, manifest 의 크기·sha256 대조)을 따르고, 사진 항목은 읽지 않는다(폰에 사진을 넣지 않음). 정본 기록·거래는 이 기기의 관측(events)과 다른 스토어(`view`, DB v4)에 두고 편집하지 않으며, 설정의 작업 공간·자료 종류와 다른 파생본과 manifest 와 정본 버전·생성 시각이 다른 거래·필지 파일은 거절한다(설정이 비어 있으면 파생본 값으로 채운다). 설정·물건·필지·기록·거래는 한 IndexedDB 트랜잭션으로 넣어 중간 실패 시 이전 상태를 유지하고, 파생본에 필지가 없으면 기존 필지를 지운다. 이력 화면(`web/app/view.js`)은 물건마다 이 기기 관측(정본에 같은 record_id 가 있으면 정본 것으로 대체)·정본 기록·확정 연결 거래를, 필지마다 지번이 일치하는 거래("이 필지")·부번이 가려진 거래("번지대, 필지 미확정")·안의 물건 이력을 연도별로 보인다. 동 전체가 가려진 거래는 어느 필지에도 붙이지 않는다. 화면과 안내 문구는 정본 버전·PC 생성 시각·가져온 시각을 보이고 "더 새 정본이 있는지는 PC 에서 확인" 을 붙이며 최신이라고 표시하지 않는다. 2026-09-27 J5-023 에서 채택.

근거: 사용자는 필지를 누르면 그 필지의 정보와 연도별 거래를 보고 싶어 하며, 재료(파생본의 기록·거래·연결)는 PC 에 이미 있었다. 파일 세 개를 따로 넣는 방식은 폰에서 번거롭고 버전이 섞일 수 있으므로 하나의 파생본을 통째로 읽어 같은 정본 버전임을 보장한다. 데이터 사전 §4·§7.2 에 따라 마스킹 거래를 특정 필지에 확정하지 않고 번지대로만 표시한다. 파일만으로는 정본이 더 새로워졌는지 알 수 없으므로(J5-017C 의 "미확인"), 폰은 단정하지 않는다.

경계: 폰은 정본을 편집하지 않는다(거래 연결·정정은 PC 명령). 사진은 파생본에 있어도 넣지 않는다(용량·개인 사진). 파생본 한도는 폰 메모리 기준(파일 256MB, 텍스트 항목 64MB)으로 PC 검사기보다 좁다. 정본에 반영된 기록은 파생본에 있다는 사실로만 "정본" 배지를 달고, 내보내기 성공을 반영 완료로 표시하지 않는다는 규칙은 그대로다.

대안: (1) 파생본 ZIP 을 풀어 파일마다 넣기: 지금까지의 방식, 버전이 섞일 수 있어 대체. (2) 폰이 정본 SQLite 를 직접 읽기: 실데이터·개인정보가 폰에 통째로 가고 SQLite 런타임이 필요해 채택하지 않음.

## ADR-18. 배경 지도는 앱 안에서 공식 타일 API 의 타일을 그리고, 받은 타일을 기기에 저장해 오프라인에서도 보인다

결정: 사용자가 "매번 외부 지도로 넘어가지 않고 앱 안에서 모든 것을 보고 싶다" 고 결정해(2026-09-27), ADR-15 가 보류했던 배경 지도를 앱 안에 넣는다. 자체 SVG 지도(ADR-12)의 맨 아래 층에 Web Mercator XYZ 타일을 `<image>` 로 그린다(`web/app/tiles.js`, `map.js`). 타일 제공자는 설정에서 사용자가 켜며(기본은 꺼짐), "직접 입력"(허용 호스트의 https 주소 또는 같은 출처의 타일 폴더)과 VWorld(국토교통부) 미리 설정을 둔다. 미리 설정은 공식 문서·실제 응답·캐시 이용조건을 확인하기 전까지 선택 불가로 둔다(AGENTS.md: 약관·승인·실제 응답을 먼저 확인). 인증키는 IndexedDB meta 에만 저장한다. 타일 URL 에는 `{key}` 자리표만 두고 서비스 워커가 요청 직전에 키를 읽어 네트워크 요청에만 넣으므로 키가 캐시 키·요소 속성·화면·로그·저장소에 남지 않는다. 요청은 코드의 허용 호스트(`TILE_HOSTS`: `api.vworld.kr`)와 같은 출처로만 가고, CSP `img-src` 도 그 호스트만 연다(정적 검사가 세 곳의 목록이 같은지 확인). 서비스 워커가 타일 요청을 가로채 캐시(`j5-tiles-v1`, 앱 캐시와 별도, 상한 6,000장)에 저장하므로 한 번 본 타일은 오프라인에서도 보이고, 설정의 "이 범위 미리 받기" 가 대상·필지 범위(여유 300 m)를 확대 14~18 단계로 미리 받는다(한 번에 3,000장 상한). 타일이 없거나 실패해도 위치점·필지·도로 배경(ADR-13·16)은 그대로다. 지도에 제공자 출처 표시를 둔다. 2026-09-27 J5-024 에서 채택.

근거: 토지이음처럼 배경 위에서 필지를 보는 것이 사용자의 목적이고, 외부 링크는 흐름을 끊는다. 네이버·카카오는 타일을 직접 받는 공식 경로가 없고(SDK 임베드만 허용) 우리 SVG 렌더러와 맞지 않으며 비공개 URL 추측은 AGENTS.md 가 금한다. VWorld 는 공식 문서화된 타일 API 이고 무료 키를 서비스 URL 에 등록해 쓴다. 통신은 사용자가 켠 제공자에게만, 켠 뒤에만 일어나므로 ADR-01 의 "숨은 통신 없음" 은 "사용자가 켠 통신만" 으로 좁혀 유지한다. 타일 캐시로 오프라인 임장 원칙을 지킨다.

경계: 타일 URL 형식은 작업 환경에서 공식 문서와 호스트 접근이 막혀 미검증이다(미리 설정에 `verified: null`, 안 보이면 제공자 문서의 형식을 "직접 입력" 에 넣는다). 제공자 약관(출처 표시, 캐시·오프라인 사용 범위, 호출 한도)은 사용자가 확인한다. 키를 URL 에 싣는 방식이라 같은 폰의 다른 사이트에는 노출되지 않지만 네트워크 상에서는 보이므로 제공자가 서비스 URL 로 키를 제한하는 것을 전제로 한다. 타일 캐시는 원본 자료가 아니고 정본·백업 대상이 아니다.

보정(J5-079, 2026-10-14): 기본 지도(`vworld_base`) 미리 설정을 켠다. 배포 주소의 iPhone Safari 에서 사용자 키로 z17 타일(256×256 PNG, 종로5가역 일대)을 받아 형식·키·서비스 URL 이 맞는 것을 확인했다(J5-078 기기 시험). 항공사진·항공사진+라벨은 확인 전이라 그대로 고를 수 없다. 빈 지도에 '배경 지도 켜기' 를 두어 설정의 배경 지도 칸(기본 지도 선택, 인증키 칸)으로 잇는다. 약관의 캐시·오프라인 사용 범위와 호출 한도는 여전히 사용자가 확인하며, 확인 전에는 이 제공자로 '이 범위 미리 받기'(한 번에 최대 3,000장)를 하지 않는다(`prefetch: false`, 리뷰 반영 PR #127). 지도를 움직여 본 타일의 저장은 이전 규칙 그대로다.

대안: (1) 외부 지도 링크만(ADR-15): 사용자 요구와 맞지 않아 보조로 강등. (2) MapLibre + 벡터 타일: 공급망 비용(ADR-12)이 크고 래스터 타일이면 자체 렌더러로 충분하다. (3) 네이버·카카오 SDK 임베드: iframe·외부 스크립트 실행이 필요해 CSP·보안 원칙과 충돌.

## ADR-19. 필지의 토지 속성은 VWorld 토지 자료 묶음에서 읽어 정본에 필지마다 한 행으로 두고, 폰은 값 그대로 보여 준다

결정: 사용자가 VWorld(국토교통부 공간정보 오픈플랫폼)에서 구역별로 내려받은 토지 자료 묶음(연속지적도형정보 dt_d002, 토지특성공간정보 dt_d194, 토지이용계획공간정보 dt_d154, 토지소유공간정보 dt_d160)을 지역 공통의 기초자료로 삼는다(2026-09-27, 사용자 제안 "이 정보들을 베이스로 기본 지도에 연결하고 개별 정보를 쌓아나가면 다른 지역도 용이"). `j5 parcels inspect/convert` 는 이 묶음(바깥 ZIP, 자료별 ZIP·SHP 하나, 또는 폴더)을 자동 인식해 `변경컬럼정보.csv` 로 열 이름(A0…)을 되돌리고 UTF-8 로 읽으며, 연속지적도로 필지 도형·지번 번들을 만들면서 나머지 세 자료의 값을 PNU 로 붙여 필지마다 `properties.attrs` 에 싣는다(`j5/parcels/vworld.py`, 번들 스키마 `$defs/attrs`·`attrs_sources`). 정본은 `parcel_attributes`(db_schema 15, 필지마다 한 행: 지목·공부면적·개별공시지가와 기준 연월·용도지역 1·2·이용상황·도로접면·지형·지역지구 목록(코드·이름·관계)·소유 구분 코드·구분명·공유인수·변동일·원인 코드·국가기관 구분, 출처 목록·출처 문서·기준일·내용 해시)에 `parcels-load` 가 함께 넣고, 공부면적은 `parcels.registered_area_m2` 에도 채운다. 파생본 `parcels.geojson` 이 같은 필드를 폰에 전달하고, 폰의 필지 패널은 값을 그대로 항목별로 보이며(결측은 "미확인"), 지도에는 용도지역 이름의 분류(주거·상업·공업·녹지 등)로 채움색을 켜고 끌 수 있다(켬 여부는 기기 저장).

근거: 토지이음이 보여 주는 정보(지목·면적·공시지가·용도지역·규제·소유구분)를 앱 안에서 필지를 눌러 바로 보는 것이 사용자의 목적이고(ADR-18 과 같은 결정), VWorld 자료는 전국 같은 형식이라 종로5가 밖의 지역도 같은 명령으로 처리된다. 실측(3구역, 724·552·1,448필지): 자료마다 열 순서가 달라 A 번호가 아니라 CSV 매핑으로 찾아야 하고, .cpg 없이 UTF-8 이며, 지역지구 이름 목록은 .dbf 열 길이(254)에 잘리므로 코드 목록을 기준으로 두고 잘림을 표시한다. 구역을 나눠 받으면 경계 필지가 양쪽에 들어 있어 같은 기준일에 도형·지번이 같고 출처 표기만 다르면 변화 없음으로 둔다(이전 규칙은 충돌로 거절). 값은 자료의 표기 그대로이며 확인·판단이 아니다(AGENTS.md "실거래·호가·현장 관측·전달정보·추정·가정을 분리", "핵심 값에 근거와 시점을 연결"): 근거는 `attrs_sources`·`source_documents`, 시점은 번들의 도형 기준일(`as_of`). '지정되지않음' 은 값 없음(null)으로 두고 0 으로 바꾸지 않는다.

경계: 토지소유공간정보의 연령대(`agrde_se_code`)·거주 구분(`resdnc_se_code`)은 읽지 않고(개인 특성), 소유자 이름·주소는 자료에 없으며 앞으로도 저장하지 않는다(AGENTS.md 보안). 공유인수·변동일은 대장의 사실 항목으로만 둔다. 용도지역 색 분류는 이름의 부분 문자열로 나눈 표시용이며 규제 판단이 아니다. 공시지가는 ㎡당 원이며 거래가·감정가가 아니다. 실제 자료·번들은 실데이터 홈에만 두고 저장소·공개 앱에는 가상 묶음(`tests/fixtures/make_parcels.py` 가 시험 때 생성)에서 만든 가상 번들만 둔다. VWorld 자료의 이용조건·갱신 주기는 사용자가 배포처에서 확인해 `--license` 로 기록한다(작업 환경에서 확인하지 못했다). 속성은 필지 도형과 별개로 바뀌므로(소유 변동, 공시지가 연 1회) 같은 기준일에도 내용이 다르면 갱신하고, 더 오래된 기준일은 거절한다. 번들에 든 자료 묶음만 갱신하며(없는 자료의 값은 유지: 자료 없음은 null 관측이 아니다) 속성 기준일 `as_of` 는 파생본에 실려 폰이 도형 기준일과 따로 보인다. 이력(J5-026): 자료 종류·기준일마다 그때 읽은 값을 `parcel_attribute_snapshots`(db_schema 16)에 그대로 쌓고(값이 같아도 새 기준일이면 한 행, 같은 기준일의 재다운로드는 값 교체) 정본·파생본이 값이 바뀐 지점만 계산해 `attrs_history` 로 싣는다. 폰 필지 이력은 그 변화를 기준일의 연도에 "토지 자료" 항목으로 보이고, PC 는 `db parcels-history <PNU>` 로 본다. 연도별 공시지가·소유 변동·용도지역 변경은 이 스냅샷에서 재구성하며, 자료를 새 기준일로 다시 내려받아 넣을 때만 쌓인다. 건축물대장·규제 고시 문서(데이터 사전 §6 의 건축물·규제 기록)는 이 속성으로 대체하지 않는다.

대안: (1) 토지이음·국가공간정보포털 조회 API: 필지마다 온라인 호출이 필요하고 오프라인 임장·캐시 조건이 맞지 않아 파일 방식을 택했다. (2) 속성을 파생본에만 두고 정본에 넣지 않기: 근거·시점·이력을 정본에서 관리해야 하고(§6 규제·권리 최소 파생값) 지역 확장의 기초자료이므로 정본 표로 두었다. (3) 자료별 별도 표(토지특성·이용계획·소유): 필지마다 한 행이면 충분하고 조회가 단순해 한 표로 합쳤다. 이력이 필요해지면 기준일별 행으로 확장한다.

정정 (J5-032, 2026-09-28): 토지이용계획의 지역지구 이름 목록(`prpos_area_dstrc_nm_list`)은 코드 목록과 위치로 짝짓지 않는다. 실측(3구역 2,724행)에서 코드 목록과 관계(포함·저촉·접함) 목록은 온전하고 1:1 이었지만, 이름 목록은 모든 행이 .dbf 열 한도(254바이트)에서 잘렸고 한 코드의 이름이 두 번 나오는 등 순서가 코드와 맞지 않았다. 그래서 정본·번들은 코드·관계 짝(`plan_zones`, 이름 칸은 비움)과 자료에 적힌 순서 그대로의 이름 목록(`plan_zone_names`, 열 한도에 닿으면 끊긴 마지막 조각은 뺌)을 따로 둔다. 폰은 이름 목록을 짝짓지 않은 채 보이고 저촉·접함은 코드로 보인다. J5-025 형식으로 이미 넣은 값은 같은 기준일의 VWorld 묶음을 다시 반영하면 교체된다. 코드→이름 공식 표는 여전히 후속 과제다.

## ADR-20. 현재 위치는 사용자가 누를 때 한 번 읽어 지도에 그리기만 하고, 저장·전송하지 않는다

결정: 임장 중 서 있는 자리의 필지를 바로 열기 위해 지도에 "현재 위치" 버튼을 둔다(J5-027). 누를 때만 브라우저 Geolocation 으로 위치를 한 번 읽어(고정밀, 15초 제한, 캐시 없음) 지도에 점과 정확도 원을 그리고, 불러온 필지 중 그 점을 품는 필지가 있으면 필지 패널을 연다. 위치·정확도·시각은 IndexedDB·기록·내보내기 어디에도 저장하지 않으며 외부로 보내지 않는다(ADR-01 의 통신 원칙 그대로). 권한은 브라우저가 묻고, 거부·실패·보안 컨텍스트 아님은 안내 문구로만 남긴다. 같은 화면의 지번·PNU 찾기는 불러온 필지 안에서만 찾는 순수 함수이며 통신이 없다. 2026-09-27 채택.

근거: 2,700필지 규모에서는 지도를 손으로 움직여 필지를 찾기 어렵고, 토지이음처럼 "여기가 어느 필지인가" 를 바로 아는 것이 현장 사용의 핵심이다. 위치는 개인 행적이므로 관측 기록에 자동으로 붙이지 않는다(관측의 대상은 물건 ID 로만 남긴다). Geolocation 은 브라우저의 로컬 API 라 앱이 외부 서비스를 부르지 않는다(기기·OS 의 위치 서비스는 사용자 설정 영역).

경계: 배경 타일(ADR-18)이 켜져 있으면 위치로 화면을 옮기지 않는다. 옮기면 현재 위치 주변의 타일 좌표를 제공자에게 요청해 위치가 간접적으로 드러나기 때문이다(리뷰 반영, PR #73). 그때는 점·정확도 원과 필지 패널만 열고 화면 이동은 사용자가 손으로 한다(손으로 옮기면 그 범위의 타일이 요청되는 것은 ADR-18 의 사용자가 켠 통신이다). 실내·고층 밀집지에서는 정확도가 수십 m 라 경계 부근에서는 옆 필지가 열릴 수 있어 정확도 원을 함께 보인다. 위치 추적(연속 감시)은 두지 않는다. 배경 타일과 달리 위치 기능은 오프라인에서도 동작한다(GPS). 실기기 Safari 의 권한 동작·홈 화면 앱 모드는 실기기 확인 항목이다.

대안: (1) 관측 기록에 위치 자동 첨부: 개인 행적 저장이라 채택하지 않음(필요하면 별도 ADR 로 사용자 승인 뒤). (2) 연속 추적으로 지도 따라가기: 배터리·행적 문제로 보류.

## ADR-21. 현장에서 필지로 만든 물건은 기기의 임시 매입 단위로 두고, 관측 패키지의 선택 파일로 넘겨 PC 가 pending 물건으로 승계한다

결정: 필지 패널의 "이 필지를 물건으로 기록" 이 이 기기에만 임시 물건(`origin: device`, 이름은 동·지번, 위치점은 필지 안의 점, PNU 참고값)을 만들고 바로 관측을 시작한다(J5-028). 기기 물건은 시드와 별도 저장소(IndexedDB `device_assets`)에 두어 시드 교체에도 남고, 기록이 없을 때만 지울 수 있다. 내보내기는 그 묶음의 기록이 가리키는 기기 물건만 `assets.new.json`(스키마 `assets_new.schema.json`, 패키지 schema_version 1.1.0)으로 싣는다. PC 검사기는 이 파일의 물건을 시드처럼 인정하고, 반영기는 정본에 없는 것만 `resolution_status=pending` 으로 만든 뒤 기록을 반영한다. 필지 연결은 `parcels-suggest`(위치점 포함) → `parcels-link` 로 확인하고, 사람이 확인하면 `db asset-confirm` 으로 확정한다. 파생본 시드에 그 물건이 돌아오면 폰은 기기 사본을 지운다(정본이 주인). 2026-09-27 채택.

근거: 데이터 사전 §2 "대상 미확인 기록에는 임시 매입 단위 ID 와 `resolution_status=pending` 을 부여하고 실제 PNU 를 채우지 않는다. R1b 에서 임시 단위를 만들고 나중의 연결 검토 이력을 남긴다" 를 구현한 것이다. 필지 수천 개가 폰에 들어오면 목록에 없는 필지를 현장에서 바로 기록할 필요가 생기고, 그때마다 PC 에서 시드를 고쳐 다시 넣는 것은 임장 흐름을 끊는다. ID 는 기기가 만든 UUID 를 그대로 승계해(시드 승계 원칙과 같다) 기록과 물건의 연결이 끊기지 않는다.

경계: 폰은 정본을 편집하지 않는다(물건을 만들 뿐, 기존 물건·연결·상태는 바꾸지 않는다). PNU 는 참고값이며 정본 연결은 PC 검토로만 생긴다. 시드에 이미 있는 ID 가 `assets.new.json` 에 오면 정본 값을 유지하고 다시 만들지 않는다. 기기 물건에는 소유자·연락처 등 개인정보 필드가 없고 스키마가 추가 필드를 거절한다. 같은 필지에 두 번 만들 수 있으나 패널이 이미 있는 물건을 보여 주므로 보통 생기지 않으며, 생기면 PC 에서 병합한다(후속). 패키지 schema_version 1.0.0 은 그대로 지원한다.

대안: (1) 시드를 PC 에서만 늘리기(현행): 현장 흐름을 끊어 대체. (2) 관측 이벤트에 PNU 만 적고 물건 없이 기록: 기록의 대상(asset)이 없어 §2 의 기록 구조와 맞지 않아 채택하지 않음.

보정(J5-062, 2026-10-13): 필지 파일이 없어도 현장 지도의 "자리 고르기" 로 지도 가운데 십자가 가리키는 한 자리를 이 기기의 임시 매입 단위로 만든다. 그 자리가 불러온 필지 안이면 그 필지 카드를 열어 위 흐름(필지에서 만들기·기존 대상 기록)을 따르고, 필지 밖이거나 필지가 없으면 `pnu` 는 null, 위치점은 십자 자리(소수 7자리), 이름은 사용자가 넣은 것(60자까지) 또는 "지도에서 고른 곳 (월-일 시:분)" 이다. 데이터 사전 §2 의 "대상 미확인 기록에는 실제 PNU 를 채우지 않는다" 와 같고, `assets.new.json` 스키마·PC 반영(`필지 PNU 미지정`)은 바뀌지 않는다. 사용자 요구(2026-10-13, PC 를 쓸 수 없는 상황에서 "필지들을 직접 선택하고 메모를 남길 수 있어야지", 폰으로 할 수 있으면 더 낫다)에 따른다. 폰이 VWorld 에서 필지 자료를 직접 받는 길은 외부 자료 요청·CSP·키 사용 범위를 바꾸므로 이 보정에 넣지 않았다.

## ADR-22. 관심 단계는 PC 정본에서만 바꾸고 변경마다 불변 이력을 남기며, 폰은 파생본의 단계를 표시·필터만 한다

결정: `assets.tracking_status` 는 PC 의 `j5 db asset-track <asset_id> <단계> [--reason] [--on]` 으로 바꾼다(J5-029). 변경마다 `tracking_changes`(db_schema 17: 이전·새 단계, 변경일, 사유, 출처, 준비 결정 ID)에 불변 행을 남기고 dataset_version 을 올린다. `purchase_ready` 로의 전환과 철회는 준비 조건 판정·결정 이력이 있는 `readiness-approve`/`readiness-withdraw` 로만 하며 `asset-track` 은 거절한다. 준비 결정도 같은 이력 표에 `decision_id` 와 함께 남고, 기존 결정은 마이그레이션에서 백필한다. `hold`·`excluded`·`archived` 로 옮길 때는 사유가 필요하다. 관찰목록은 `watch`·`detailed_review`·`purchase_ready` 세 단계로 정의하고 `db watchlist` 가 단계별 수·관찰목록을 보인다. 파생본 시드(`assets.seed.json`)는 물건마다 `tracking_status`·`resolution_status` 를 정본 출력값으로 싣고, 폰은 이를 배지로 보이며 "전체/관찰목록만" 필터(선택은 기기 meta)를 목록·지도·다음 대상에 같이 적용한다. 폰은 단계를 바꾸지 못하고 관측 패키지에도 단계 변경은 없다. `db load-seed` 는 이 두 필드가 든 시드를 거절해 파생본 시드가 정본 입력으로 되돌아오지 않게 한다. 2026-09-27 채택.

근거: 데이터 사전 §2 관심 단계 8종과 "매물 출회 상태와 분리", §3.1 "관심도 갱신은 허용하지 않는다"(폰→PC 방향), 릴리스 계획 §8 R2 "배경 목록과 30~50개 정기 관찰목록을 구분", §11 "관찰목록 30~50개는 운영 목표". 필지 수천 개와 기기 물건이 들어온 뒤 현장에서 다시 볼 물건을 배경 목록과 나눌 필요가 생겼다. 단계 변경은 판단이므로 시점·사유를 남겨야 하고(ADR-07 의 결정 이력과 같은 원칙), 준비 상태는 이미 조건 판정이 있는 명령이 있으므로 우회 경로를 두지 않는다.

경계: 단계는 표시·분류이며 매입 판단·조건 충족이 아니다. 폰의 필터는 이 기기 화면의 선택이며 정본·다른 기기에 영향이 없다. 관찰목록 상한 50개는 경고 문구일 뿐 막지 않는다. 관심 단계 변경이 물건의 기록·연결·거래를 바꾸지 않는다.

대안: (1) 폰에서 단계 변경을 패키지로 보내기: R1 교환 범위(신규 관측만)를 넘고 충돌 병합이 필요해 제외. (2) 이력 없이 `assets` 열만 갱신: 왜 뺐는지 남지 않아 제외. (3) 파생본 `assets.geojson` 의 속성만 폰이 읽기: 위치점 없는 물건의 단계가 빠지고 시드와 두 벌이 되어 제외.

## ADR-23. 정본은 여러 지역의 필지를 담고, 폰 파생본에는 정한 법정동 범위와 물건이 연결된 필지만 싣는다

결정:
- 정본 필지 상한을 폰 상한(8,000)에서 떼어 `CANONICAL_MAX_PARCELS`(100,000)로 둔다(J5-039).
- 폰 파생본(`parcels.geojson`)에 실을 범위는 `j5 db phone-scope --emd <법정동 코드,…>` 로 정하고 정본 meta `phone_parcel_scope` 에 둔다. 실리는 필지는 그 법정동의 필지와, 범위 밖이어도 기준일에 유효한 물건 연결이 있는 필지다.
- 범위를 정하지 않으면 이전과 같이 전체를 싣는다.
- 실릴 필지가 폰 상한을 넘으면 `project` 가 게시하지 않고 이전 파생본을 유지하며, 범위를 정하라고 안내한다.
- 범위를 정했으면 번들 `warnings` 에 "폰 범위: 정본 필지 N개 중 …" 을 적고, 폰은 그 글을 필지 안내에 그대로 보인다.
- 범위가 실제로 바뀌면 dataset_version 을 올린다. 범위는 정본 meta 에 있고 파생본 내용을 바꾸므로, 이전 범위로 만든 파생본·백업이 최신으로 표시되지 않게 기존 구본 판정을 그대로 쓴다(PR #86 리뷰 반영). 같은 범위를 다시 주면 바꾸지 않는다.
- 2026-09-28 사용자 결정으로 채택.

근거: 큰 목표는 필지마다 정보·거래를 연도별로 쌓고 다른 지역도 같은 방식으로 처리하는 것이다. 정본과 폰이 같은 상한을 쓰면 비교 지역을 더할 때 정본 반영이 거절되어, PC 조회(`parcels-find`·`parcels-history`)까지 막힌다. 폰의 한계(SVG 성능·저장 공간)는 파생본 쪽 문제이므로 파생본에서 줄인다. 연결된 필지를 범위와 무관하게 싣는 이유는 현장에서 기록할 물건의 필지가 폰에서 빠지지 않게 하려는 것이다.

경계: 폰의 조건 찾기·필지 찾기는 실린 필지 안에서만 동작한다. 폰에 없는 필지는 폰에서 "없음" 으로 판단하지 않는다(안내 글). 번들 한 개의 상한(스키마 8,000)은 그대로다. 정본 조회 성능은 수만 필지에서 실측이 필요하다.

대안: (1) 폰 상한 8,000 유지: 비교 지역을 정본에 못 넣어 제외. (2) 지역마다 정본 분리: 지역 간 비교·백업이 여러 벌이 되어 제외. (3) 폰이 여러 파일을 나눠 받기: 폰 저장·검증 규칙이 커져 제외.

## ADR-24. 폰 앱은 Cloudflare 에 web/ 폴더만 정적 HTTPS 로 올리고, 사용자 도메인의 하위 주소로 연다

결정:
- 공급자는 Cloudflare Pages(무료 요금제, 실제로 만든 방식은 아래 J5-060 보정의 Workers 정적 자산). 비공개 저장소를 Git 연동하고, 빌드 명령 없이 `web/` 폴더를 그대로 게시한다. 운영 판은 `main` 브랜치다(J5-059).
- 주소는 사용자 도메인의 하위 주소 `j5.dooduk.com` 이다. 도메인의 루트(`dooduk.com`·`www`)는 사용자의 다른 용도(재무관리)로 두고 이 저장소에서 다루지 않는다. 하위 주소는 CNAME 하나로 연결되어 루트의 연결을 바꾸거나 없애도 영향이 없다. HTTPS 인증서는 공급자가 발급·갱신한다.
- 응답 헤더는 `web/_headers` 에 둔다: 다른 사이트의 틀 안에 넣지 못하게(frame-ancestors·X-Frame-Options), 형식 추측 금지, 주소 정보 안 보냄, 위치 권한은 이 앱에서만, 앱 진입점·서비스 워커는 매번 새로 확인.
- 이 공급자는 `./index.html` 을 `./` 로 넘긴다(308). 서비스 워커는 넘겨받은 응답(설치 때 캐시한 것과 네트워크에서 받은 것)을 탐색에 그대로 돌려주지 않고 같은 본문으로 새 응답을 만든다(그대로 돌려주면 브라우저가 페이지를 열지 않는다). `tests/web/deploy.e2e.test.mjs` 가 같은 넘김을 하는 서버로 확인한다.
- 보정(J5-060, 2026-10-13): 사용자가 대시보드에서 만든 프로젝트는 Pages 가 아니라 Workers 정적 자산(배포 명령 `npx wrangler deploy`, 루트 디렉터리 `/`)이다. 설정 파일이 없으면 wrangler 가 폴더를 추측한다(4.149.0 은 `web` 을 골랐다). 추측에 맡기지 않도록 저장소 루트의 `wrangler.jsonc` 에 Worker 이름 `project-j5`, 올리는 폴더 `./web`, 서버 코드 없음(`main`·바인딩 없음), 없는 주소는 404 를 적는다. `_headers` 는 같은 규칙으로 적용되고 파일 자체는 올리지 않는다. Workers 의 사용자 지정 도메인은 도메인(dooduk.com)이 Cloudflare 의 DNS 영역이어야 한다(Pages 는 바깥 DNS 의 CNAME 으로도 하위 주소를 연결한다). 사용자는 DNS 를 옮기지 않기로 했고(등록처 가비아), 주소는 우선 `project-j5.<계정>.workers.dev` 다. 계정 하위 이름은 사용자 이름이 드러나지 않게 `j5map` 으로 바꿨다(2026-10-13, 주소 `https://project-j5.j5map.workers.dev/`). `j5.dooduk.com` 연결은 보류한다.
- 게시되는 것은 코드·문서·가상자료뿐이다. `tests/test_web_publish.py` 가 web/ 안의 파일 형식과 data/ 의 가상자료 표시를 검사한다.
- 서버 API·서버 저장은 없다. 실데이터(정본·파생본·사진·키)는 지금처럼 PC 에서 만든 파일을 폰이 가져와 폰 안(IndexedDB)에만 둔다.
- 보정(J5-078, 2026-10-14): 사용자가 폰에서 필지를 바로 조회하는 온라인 방식을 골랐다("온라인 조회로 전환"). 결정 전에 VWorld 를 어디서 부를 수 있는지 쟀다. Cloudflare Worker(`/api/vworld/probe`, PR #125)에서는 요청자가 한국이어도 처리 위치가 도쿄(NRT)였고 VWorld 요청 셋이 모두 520(연결 끊김)이었다. 폰(iPhone Safari, 배포 주소)에서는 배경 타일 그림은 받았고 데이터 API 의 다른 출처 요청은 막혔다(Load failed). 그래서 Worker 를 거치는 구조는 쓰지 않고 Worker 코드와 시험 주소를 지웠다(배포는 다시 정적 자산만). 데이터 API 는 같은 출처 권한이 없는 격리 프레임(`vworld-frame.html`, sandbox=allow-scripts)에서 JSONP 로 부르는 방법을 기기 시험 페이지에서 잰다. 이 프레임 주소만 `_headers` 에서 같은 출처의 틀을 허용한다. 온라인 조회의 구조는 이 결과로 ADR-27 에서 정한다.
- 접속을 본인으로 제한하고 싶으면 Cloudflare Access(무료 한도)로 이 주소에 로그인을 걸 수 있다. 앱 동작과는 무관하다.
- 2026-10-13 사용자 결정(공급자 Cloudflare, 하위 주소, 도메인 dooduk.com 의 루트는 재무관리용)으로 채택. ADR-01 의 "공급자는 계정 확인 후 확정" 을 이 결정으로 채운다.

근거: 지금은 PC 의 정적 서버를 같은 Wi-Fi 에서 `http` 로 열어야 해서 PC 가 꺼져 있거나 밖에 있으면 앱이 열리지 않는다(사용자 확인: 앱 주소가 열리지 않음). `http` 주소는 보안 컨텍스트가 아니어서 서비스 워커(오프라인 실행)·현재 위치·WebCrypto 를 쓸 수 없다. 정적 HTTPS 게시는 ADR-01 의 "코드 전용 HTTPS 배포" 그대로이고 앱 구조를 바꾸지 않는다. Cloudflare Pages 는 비공개 저장소에서 폴더 하나만 게시할 수 있고(GitHub Pages 는 비공개 저장소에 유료 요금제나 공개 사본이 필요하다) 사용자 도메인 연결과 HTTPS 가 자동이다.

경계: 폰의 기록은 주소(origin)마다 따로 저장된다. 예전 `http://<PC 주소>:8000` 에 남은 기록은 새 주소에서 보이지 않으므로 옮기기 전에 모두 PC 로 보낸다(J5-017D 순서). 배경 타일 키(ADR-18)를 쓰면 제공자에 새 주소를 서비스 URL 로 등록한다. 게시한 코드는 그 주소에서 누구나 볼 수 있다(Access 를 걸지 않으면). 브랜치마다 미리 보기 주소(`<브랜치>.<프로젝트>.pages.dev`)가 생기며 내용은 같은 코드다.

대안: (1) GitHub Pages: 비공개 저장소는 유료 요금제가 필요하거나 web/ 만 공개 저장소로 옮겨야 한다. (2) Netlify: 기능은 비슷하나 사용자가 Cloudflare 를 골랐다. (3) 서버가 자료를 보관하고 폰은 조회만 하는 웹서비스: PC 정본·폰 저장 구조(ADR-01·02·17)를 바꾸고 실데이터를 외부에 두게 되므로 새 ADR 과 별도 승인이 필요하다.

## ADR-25. 가격 적정성은 자동 추정가 없이 주변 실거래 단가와 공시지가 배율의 근거로 보인다

결정: 폰 필지 카드의 "주변 사례"(J5-064)는 같은 시군구·같은 법정동의 실거래를 기간 안에서 모아 평당 단가(대지·연면적)의 중간값·범위와 사례 목록을 보인다. 지번이 온전해 필지가 정해지는 거래만 그 거래 연도 이하의 가장 늦은 기준연도 공시지가로 "대지 ㎡당 거래가 ÷ 공시지가" 배율을 구하고(늦은 해의 공시지가로 거슬러 쓰지 않는다), 배율 사례가 3건 이상이고 이 필지의 공시지가가 있을 때만 "이 필지 공시지가 × 배율 중간값" 을 참고 추정으로 적는다. 참고 추정 줄에는 공시지가 값·기준연도·배율·사례 수와 "추정값이며 시세 판단이 아님" 을 함께 적는다. 지분 거래는 단가·배율에서 뺀다. 저평가 판정·매수가 제안·회귀 모형은 만들지 않는다.

근거: 사용자 요구(2026-10-13) "매매 이력과 근처 매각 사례를 통해 가격 적정성 검토". 다른 서비스의 저평가 표시는 모형 추정이라 근거를 확인할 수 없다. AGENTS 는 실거래·추정·가정을 분리하고 핵심 값에 근거와 시점을 잇도록 한다. 공시지가 배율은 사례마다 계산 근거가 화면에 드러나고 PC 정본 자료(실거래·토지특성)만으로 재현된다.

경계: 배율은 같은 동 안에서도 도로 접면·용도·건물 상태에 따라 크게 다르다. 참고 추정은 정본에 쓰지 않고 목표 매수가 기록(`target_price`)을 대신하지 않는다. 사례가 적은 동·기간에서는 값을 내지 않는다. 번지대 거래는 단가 통계에는 들고 배율에는 들지 않는다.

대안: (1) 자동 추정가(AVM): 모형·검증 자료가 없어 제외. (2) 반경 기준 사례: 가린 지번 거래는 위치가 없어 반경을 잴 수 없으므로 법정동 기준으로 둔다.

보정(J5-067, 2026-10-13): 주변 사례에 추이 그래프를 더한다. 같은 동 거래의 대지 평당 단가(점)와 이 필지 공시지가의 평당 환산(기준연도 1월 1일부터 다음 기준연도까지의 계단선)을 한 축(원/평)에 그린다. 두 값은 모두 사실 자료이며 추세선·회귀선·예측 구간은 그리지 않는다. 같은 값은 그래프 값 표와 사례 목록에도 있어 그래프 없이 읽을 수 있다.

보정(J5-071, 2026-10-13): 주변 사례에 같은 동 연도별 시세를 더한다. 기간이 시작하는 해의 1월 1일부터 올해까지 달력 연도마다 같은 동 거래의 대지 평당 중간값(사례 수·최저~최고)과 거래 수를 막대로 보이고(값은 고를 수 있다), 그해 이 시군구에서 그 종류를 받은 개월을 함께 적는다. 받지 않은 해의 거래 수는 0 이 아니라 미수집이다. 시작·최근 변동은 대지 평당 사례가 3건 이상인 가장 이른 해와 가장 늦은 해의 중간값끼리만 적고, 그런 해가 둘보다 적으면 사유를 적는다. 연도별 중간값은 실거래 집계이며 동 시세 지수·추정가가 아니다. 다른 서비스(사용자가 보여 준 화면)의 "추정가"(토지+건물 자동 추정)는 대안 (1)과 같아 넣지 않는다.

보정(J5-072, 2026-10-13): 같은 값을 PC 정본에서 `db parcels-comps` 로 낸다(근거 "PC 정본 자료만으로 재현된다" 의 명령). 규칙은 폰과 같고 대조 시험이 지킨다. PC 는 범위 규칙과 무관하게 정본의 같은 동 거래를 보므로 범위 밖 동의 필지도 사례가 있다.

## ADR-26. 실거래 수집 종류를 단독·다가구·토지 매매로 넓힌다

결정: PC 수집기·정본 반영에 단독·다가구 매매(`RTMSDataSvcSHTrade`)와 토지 매매(`RTMSDataSvcLandTrade`)를 상업·업무용 매매와 같은 틀로 더한다(J5-065). 종류 등록부(`j5.collect.rt.KINDS`)가 종류마다 제공자·기본 주소·원본 폴더를 정하고 명령은 `--kind` 로 고른다(기본 상업·업무용, 생략하면 이전과 같다). 반영은 실행 기록의 제공자와 폴더의 종류가 다르면 거절하고, 종류마다 식별 필드와 열 대응을 둔다. 상업·업무용 거래의 식별 해시는 바꾸지 않아 이미 정본에 있는 거래가 새 거래로 갈리지 않는다. 다른 종류의 식별 해시에는 제공자를 넣는다. 응답에서 사라짐·범위 현황·최근 수집은 같은 종류의 실행끼리만 본다. 정본 스키마는 바꾸지 않는다(종류는 이미 있는 provider 열이다). 폰 파생본은 거래마다 종류(`deal_kind`)와 토지 지목을, 수집 개월마다 종류별 완전 수집 개월(`kind_months`)을 싣는다. 형식 버전은 1.0.0 그대로이며 이 칸이 없는 이전 파일도 받는다.

근거: 사용자 결정(2026-10-13) "수집 종류 늘리기". 종로5가 일대는 상업·업무용 건물 사이에 단독·다가구 주택과 나대지 거래가 섞여 있어, 상업·업무용만으로는 필지 연도별 거래와 주변 사례가 빈다. 세 API 는 같은 기관의 같은 요청 단위(시군구·계약월·페이지)라 수집·체크포인트·원본 보존 규칙을 그대로 쓸 수 있다.

경계: 단독·다가구·토지의 주소와 응답 필드 이름(`totalFloorAr`·`houseType`·`dealArea`·`jimok`)은 공식 명세를 이 컨테이너에서 열어 확인하지 못한 가정이다. 첫 실제 응답의 표본 요약으로 확인하기 전까지 그 값은 null 과 사유일 수 있다. 주변 사례(ADR-25)는 종류를 가리지 않고 같은 동의 거래를 모은다. 토지 거래는 토지 면적으로 대지 평당 단가와 공시지가 배율에 들고 연면적 단가에서는 빠진다. 사례 목록에는 종류(토지·단독·다가구·근린 등)를 적는다. 건물값이 든 거래와 토지만의 거래를 한 중간값에 섞는 영향은 실자료로 본 뒤 종류별로 나눌지 정한다. 아파트·연립다세대·오피스텔·분양권은 넣지 않는다(집합건물 단위 거래라 필지 매입 검토와 거리가 멀다).

대안: (1) 종류마다 별도 모듈: 같은 규칙을 세 번 쓰게 되어 제외. (2) 정본에 종류 열을 새로 만드는 마이그레이션: provider 가 이미 종류를 가리므로 제외.

보정(J5-066, 2026-10-13): 섞을지 나눌지를 기본값으로 정하지 않고 폰에서 고르게 한다. 지도 실거래 줄과 필지 카드의 주변 사례에 같은 종류 고르기(모든 종류·상업·업무·단독·다가구·토지)를 두고 이 폰에 저장한다. 기본은 모든 종류다. 거래 파일에 종류가 둘 이상일 때만 보이고, 종류 칸이 없는 이전 파일의 거래는 상업·업무용으로 본다.

보정(J5-073, 2026-10-14): 파생본 수집 개월에 종류마다 시도한 개월(`kind_months_any`)을 더한다. 종류를 고른 폰 연도별 시세가 그 종류를 시도했다 실패한 해와 시도하지 않은 해를 PC `parcels-comps` 처럼 가른다(J5-072 리뷰에서 남긴 "모름"). 형식 버전은 1.0.0 그대로이며 이 칸이 없는 이전 파일은 이전처럼 "모름" 이다.

## ADR-27. 지도를 누른 자리의 필지는 폰이 VWorld 데이터 API 를 격리 프레임의 JSONP 로 불러 보인다

결정: 사용자가 폰에서 필지를 바로 조회하는 온라인 방식을 골랐다(2026-10-14, "온라인 조회로 전환", 누른 자리의 좌표가 VWorld 로 전송되는 것을 승인). 현장 지도의 빈 곳(대상·거래·불러온 필지가 아닌 곳)을 누르면 그 자리의 경도·위도로 VWorld 2.0 데이터 API 의 연속지적(`LP_PA_CBND_BUBUN`)과 용도지역(`LT_C_UQ111`)을 부르고, 필지 경계를 지도에 그리며 시트 카드에 주소·지번·지목·공시지가(원/㎡·평 환산, 기준 연월)·도형면적·용도지역 원문을 보인다. 카드에서 "이 필지를 대상으로 기록" 으로 이 폰의 대상을 만든다(ADR-21 과 같은 흐름). 호출은 같은 출처 권한이 없는 격리 프레임(`vworld-frame.html`, `sandbox="allow-scripts"`)이 JSONP(응답을 스크립트로 받는 방식)로 하고, 프레임은 부모가 보낸 값을 검사해(자료는 위 둘만, 좌표는 한국 범위, 키 형식) 정해 둔 주소만 만들며 응답을 JSON 으로 한 번 복사해 결과 값만 돌려준다. 앱은 그 프레임에서 온 메시지만 받는다. 인증키는 배경 지도에 넣은 VWorld 키(ADR-18, 이 폰에만 저장)를 쓰고 `domain` 은 앱 주소다. 조회 결과는 화면에만 두고 저장하지 않으며, 늦게 온 응답은 마지막으로 누른 자리의 것만 보인다. 2026-10-14 J5-080 에서 채택.

근거(실측, J5-078): 클라우드 작업 환경과 Cloudflare Worker(처리 위치 도쿄)에서 VWorld 는 모두 연결을 끊었다(502·520). 폰(iPhone Safari, 배포 주소)에서 배경 타일 그림은 받았으나 데이터 API 의 일반 요청은 다른 출처 허용 머리글이 없어 막혔고(Load failed), 격리 프레임의 JSONP 는 응답을 받았다(필드: `pnu`·`addr`·`jibun`·`bonbun`·`bubun`·`jiga`·`gosi_year`·`gosi_month`, 경계는 경위도 MultiPolygon). JSONP 는 VWorld 가 준 스크립트를 실행하므로 앱 문서에서 돌리면 앱의 저장소(기록·사진)에 닿을 수 있다. 같은 출처 권한이 없는 프레임 안에서만 돌려 저장소·쿠키와 떼어 놓는다.

경계: 값은 그때 조회한 VWorld 연속지적도이며 공부(대장) 확인이나 법률 판단이 아니다. 면적은 경계로 계산한 도형면적(수 ㎡ 오차)이고 공부면적과 다르다. 지목은 지번 글 뒤에 붙은 글자를 그대로 쓴다. 용도지역 자료의 필드 이름은 아직 실측 전이라 받은 속성을 이름 그대로 보인다(실측 뒤 정리). 결측은 0 이 아니라 "미확인" 이다. 오프라인이면 조회하지 않는다. VWorld 이용약관의 호출 한도·저장 범위는 사용자가 확인한다(ADR-18 경계와 같다). 정본·파생본·PC 수집 경로(ADR-13·19)는 바꾸지 않는다: 온라인 조회는 현장 확인용이고 PC 정본의 근거가 되지 않는다. 같은 자리의 VWorld 일반 요청(다른 출처 허용)이 열리면 격리 프레임 없이 바로 부르는 쪽을 다시 본다.

보정(J5-081, 2026-10-14): 배경 지도가 VWorld 기본 지도이고 확대 17단계 이상이면 지도가 멈춘 뒤 덮이지 않은 영역(사방 25% 여유, 한 변 0.02° 이하)의 연속지적을 범위(BOX, 한 번에 최대 1,000필지)로 같은 격리 프레임에서 받아 경계와 지번(18단계 이상, 필지가 충분히 클 때)을 그린다. 다 받은 범위는 기억해 그 안에서는 다시 부르지 않고, 필지는 화면에만 두며 4,000개를 넘으면 오래된 것부터 버린다. 경계는 탭 대상이 아니라서 누르면 그 자리를 조회한다(ADR-27 본문). 용도지역은 실측한 필드(`uname`·`dyear`)로 카드에 한 줄로 보이고(같은 이름은 한 번), 원문 목록은 접힌 칸에 남긴다.

대안: (1) Cloudflare Worker 가 키를 쥐고 대신 부름: VWorld 가 해외 처리 위치의 연결을 끊어(520) 쓸 수 없다. (2) 국내 서버(사용자 PC·국내 클라우드)를 중계로 둠: 운영·비용·가동 시간이 들고 실데이터 외부 보관 문제가 생긴다. (3) 앱 문서에서 JSONP 를 바로 실행: 외부 스크립트가 앱 저장소에 닿는다. (4) PC 파일 경로만 유지(ADR-13): 사용자가 실사용과 멀다고 판단했다(지도에서 필지 조회·선택 불가).
