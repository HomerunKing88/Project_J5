# 릴리스 계획과 인수조건

버전 1.2 / 2026-09-22. 문서 단계이며 완료된 코드나 실제 기기 성능을 뜻하지 않는다. 저장소명은 `<actual-repository>`로 표시하고 J5-001에서 확인한다.

## 1. 개발 순서

```text
R0  저장소·기기·기본 데이터 경로 확인
R1a 소수 물건의 현장 기록·사진·단일 파일 내보내기
R1b 단방향 정본 반영·중복 방지·백업·복구
R2  핵심 기초자료·경로와 표본틀·파생본 관리
R3  거래 수집·장기 소급·연결·취소·정정
R4  이중 시점 조회·사진·목표 매수가·투자판단
R5  규제·개발안·공동매입·필요현금 비교
R6  휴면·이전·복구 운영 검증
R7  매입 준비 체크리스트·검토자료·상태 재검증
```

R1a 이후 실제 임장 수집 시험을 시작한다. R1b 이전 기록은 내보낸 파일과 별도 사본으로 보관하며 정본 운영이 완료된 것으로 설명하지 않는다. 코드 작업과 임장을 순차적으로 모두 기다리게 하지 않는다.

R2에서 매입 준비 체크리스트를 수동 기록으로 사용할 수 있게 하고, 실제 매입 검토가 시작되면 R7을 앞당긴다. R7은 특정 연도에 자동 실행되는 일정이 아니다. 고급 거래 화면이 미완성이어도 근거를 수동 입력해 체크리스트를 쓸 수 있게 한다.

## 2. 공수 예산과 재추정

아래는 구현·검토·자동 및 수동 테스트를 포함하는 신규 예산 추정이다. 실제 구현 실적, 신뢰구간, 납기 확약이 아니다. API 승인 대기, 실제 거래 전수 매칭, 정기 임장, 전문가 상담·계약 검토, 대량 원본자료 정리는 별도다.

| 릴리스 | 기본 순작업 예산 | 제외하거나 미루는 항목 |
|---|---:|---|
| R0 | 6~10시간 | 20개 물건의 완전 실사·전체 API 승인 대기 |
| R1a | 16~28시간 | 정본 DB·반영확인서·충돌 UI·대량 사진 처리 |
| R1b | 20~36시간 | 다기기 수정·부분 승인·변경 병합 |
| R2 | 28~44시간 | 비교 블록 전체 대장 수집·경로 편집기 |
| R3 | 32~48시간 (R0 실측 후 조정, §7) | 전 거래 자동 PNU 확정·가격 예측·연결 검토 화면 |
| R4 | 32~48시간 | 전 기간 부드러운 지도 애니메이션 |
| R5 | 36~60시간 | 자동 건축설계·허가·세무·은행 승인 판정 |
| R6 | 12~20시간 | 사용하지 않는 모든 OS·브라우저 지원 |
| R7 | 12~20시간 | 실제 전문가 실사·계약 대행·자금 실행 |
| 합계 | 202~330시간 | 실제 자료 정리와 운영 별도 |

미확인 기기·자료 형식 등에 대한 계획 예비 20%를 더하면 약 240~400시간이다. 이 예비율은 프로젝트 관리 가정이다. 클로드의 전체 300시간대 추정을 실제 실측으로 채택한 것은 아니다.

R0+R1a는 기본 22~38시간이다. 주 6~8시간이면 단순 나눗셈상 약 3~7주, 예비를 포함하면 약 4~8주다. 실제 기기 시험·승인·사용 가능 시간에 따라 달라진다. R1b 포함 운영 준비는 별도 마일스톤이다.

각 PR에 `예상·실제 시간, 재작업 이유, 미확인 변수, 남은 인수조건`을 기록한다. 초기 3개 PR 후 잔여 작업을 다시 산정한다. 초과하면 기능을 줄이거나 릴리스를 나누고 안전 검사를 조용히 삭제하지 않는다. 문서 분량이나 AI 코드 생성 속도로 전체 소요시간을 역산하지 않는다.

## 3. 첫 작업과 저장소 구조

J5-001에서 실제 레포 URL·이름·기본 브랜치·기존 구조·공개 여부를 읽는다. PC OS·폰 OS·주 브라우저·파일 전송·백업 위치도 확인한다. 이 지침은 v1.0에도 있었으며 이번에는 예시 저장소명을 실제 이름처럼 사용하는 부분을 제거했다.

```text
<actual-repository>/
  README.md / AGENTS.md
  docs/ADR.md / DATA_DICTIONARY.md / RELEASE_PLAN.md
  web/          정적 앱·고정 vendor·가상자료만
  j5/           Python 수집·반영·검증·내보내기·백업
  sql/          필요한 단계의 마이그레이션
  schemas/      관측·패키지·정본 기록 계약
  tests/        단위·통합·기기 시험·가상 fixture
  config/       민감정보 없는 설정 예시
```

실제 데이터 폴더는 레포 밖이다. 빈 후속 모듈을 미리 대량 생성하지 않는다. 버전은 app, db_schema, package_schema, dataset, projection_schema, calculation으로 역할을 구분한다.

첫 PR은 저장소 적합성·문서·보안 허용목록·관측 스키마와 가상 fixture까지만 한다. 지도·IndexedDB·PC 반영·복구를 모두 첫 PR에 넣지 않는다. 실제 파일이 있는 레포의 README나 AGENTS를 내용 확인 없이 덮어쓰지 않는다.

## 4. R0와 R1a: 첫 임장 수집 시험

R0에서 실제 기기의 파일 선택·저장·사진 형식을 작은 시험으로 확인한다. 사용자 승인된 정적 HTTPS 환경 또는 시험 가능한 경로를 정한다. 미확인 외부 타일·실데이터 공개 배포는 사용하지 않는다.

R0 통과조건: 최근·중간 시점·2006년의 표본 월 3개 API 응답으로 핵심 범위와 비교 블록의 월평균 거래 행수, 주소 공개 수준, 거래 범위 분포를 실측한다. 측정 결과를 근거로 R3 범위와 공수 40~64시간을 조정한다. 핵심 범위와 비교 블록을 합친 연결 검토 대상이 연 30건 내외로 낮으면 R3의 연결 검토 화면을 만들지 않고 CSV 목록과 수동 확인으로 대체한다.

R1a는 가상 물건 5개로 시작한다. 실제 사용 전에는 허용된 자료와 사용자의 수동 확인으로 소수 실제 대상을 준비한다. 필지 경계를 못 구했으면 확인된 위치점·목록으로 기록하며 가상 도형을 실제 지적 경계로 표시하지 않는다.

R0의 20개 표본은 자료 확보 가능성 검증용이며 첫 임장 대상 목록과 구분한다. 첫 임장 대상은 한 번의 보행으로 연속 방문 가능한 5~8개로 한정하고, 지리적으로 흩어진 대상은 목록에 넣지 않는다.

구현: 지도/목록·대상 선택, 관측 상태·사진·짧은 메모, IndexedDB, 최소 앱 캐시, 경로 버전 ID 선택, 고정 이벤트 내보내기, ZIP 해시·사진 검사 도구. 필수 입력은 대상·시각·관측 상태이며 변화 확인에는 사진 또는 설명을 요구한다.

인수: 실제 폰에서 저장 후 앱을 닫고 다시 열어 기록을 확인한다. 인터넷을 끊어 준비한 목록과 기록을 사용한다. ZIP을 내보내 PC에서 기록·사진을 검사하고 독립 사본을 보관한다. 조회자료를 교체해도 현장 기록이 남는다. 미지원 사진·저장공간 부족을 실패로 표시한다.

R1a 기록은 이후 수정 없이 R1b로 반영한다. 공공 API 전량 수집·완전한 매물 정보·자동 경계 확보를 이 단계 통과조건으로 두지 않는다.

## 5. R1b: 정본과 복구

구현: 필요한 최소 SQLite 테이블·관측 반영기·단방향 멱등 처리·조회 패키지 생성·버전 표시·백업·복구. 동일 이벤트의 파일 내 순서가 바뀌거나 ZIP이 다시 만들어져도 관측을 중복 추가하지 않는다.

인수: 정상 입력 한 번, 같은 파일 두 번, 같은 ID·다른 내용, 누락 사진, 사진 복사 후 DB 실패, DB 반영 후 파생본 실패, 백업 실패를 시험한다. 처리 결과를 분리하고 원본 입력을 보존한다. 빈 폴더 복구 후 기록 수·해시·사진 연결을 확인한다.

폰 반영확인서·기준 버전별 수정 충돌·부분 승인 UI·다기기 편집은 만들지 않는다. 정본 반영 결과는 PC에서 확인한다. 실제 두 차례 임장 후 사용성 결함을 고치고 일반 운영으로 전환한다.

## 6. R2: 기초자료와 조사 표본

핵심 범위의 허용된 필지·건축물 자료를 수집·정규화한다. 총괄/개별 대장·다필지 관계·외부 ID 변경·도형 면적 차이를 검토한다. 배경 목록과 30~50개 정기 관찰목록을 구분한다.

경로 버전·점포 ID·표본틀·조사 세션·미조사 상태를 구현한다. 경로와 표본의 수동 편집으로 충분하며 길찾기와 자동 경로 추천은 제외한다. 샘플 고정·변경 이력을 남기고 공통 표본 비교를 제공한다.

파생본의 전량 재생성·버전 일치·실패 시 이전본 유지 규칙을 구현 또는 보강한다. 실제 필요가 확인되면 읽기용 테이블을 추가한다. 수동 매입 준비 체크리스트의 기록 형식을 도입한다.

인수: 표본 추가·탈락·점포 통합·조사 누락이 공실로 잘못 집계되지 않는다. 같은 점포를 두 구간에서 세지 않는다. 파생본 실패 후 정본·이전본의 버전이 그대로 표시된다.

## 7. R3: 거래와 장기 자료

공식 API의 승인·실제 필드·오래된 월 지원을 확인한다. 최근 약 5년부터 수집해 조회한 뒤 목표 2006-01까지 단계적으로 확장한다. 시군구·월 응답을 같은 구의 비교 블록 사이에 재사용한다.

거래 원본·정규화·범위·연결 근거·취소·정정·검토 결정을 구현한다. 주소가 마스킹되면 미확인으로 남긴다. 비교 블록은 거래 우선이고 지정 대상에만 공시지가·필지·대장·규제를 추가한다.

인수: 정상 0건·API 실패·중간 페이지 누락이 구분된다. 일괄거래 총액·지분·구분상가·같은 값의 별개 원본 행이 올바르게 처리된다. 수집 완료기간과 물건 연결 완료건수를 따로 표시한다. 과거 대화의 거래표는 재검증 없이 넣지 않는다.

반영확인서·다기기 기능은 R3의 기본 작업에 추가하지 않는다. 필요가 발생한 경우 별도 ADR과 공수 승인을 받아야 한다.

R0 실측 결과 조정(2026-09-25, `docs/worklog/J5-014.md`): 표본 월 3개 실측에서 매입 검토 단위의 연결 검토 대상이 연 25~45건으로 §4 의 기준(연 30건 내외)에 있어, 연결 검토 화면을 만들지 않고 CLI 의 CSV 후보 목록과 수동 확인으로 대체한다. R3 기본 예산을 40~64시간에서 32~48시간으로 낮춘다. 일반건축물 지번은 전 시기 마스킹이고 집합건물 지번은 최근 월에만 공개가 확인됐으므로, 마스킹 행은 법정동·지번 앞자리 범위로만 좁힌다.

## 8. R4~R6: 분석과 운영

R4는 관측 T와 당시 기록 K를 구분한 조회, 사진 연차 비교, 목표 매수가 수정·근거 이력, 10항목 투자판단, 반대 증거와 변경 조건이다. 늦게 입력한 과거 거래·나중에 철회한 연결이 당시 기록 화면에 잘못 들어가지 않아야 한다.

R5는 법정 산정 대지·배치 영역·규제 버전·용적률 여유면적·건축사 검토안·공동매입·유지/리모델링/신축 비교·후보별 현금표·CSV다. 보증금 총액/순액, 반환 의무, 부가세·비용 중복, 공사기간 공실, 감정가 차이를 시험한다.

R6은 반기 운영 점검, 정본·사진 복구, 새 폰·PC·도메인 이전, 구패키지 열람, 외부 서비스 중단, 연말 개방형 포맷 보존본이다. 마지막 정상 앱·DB·스키마·도구 버전을 저장한다. 운영 체크는 R1b부터 시행하며 R6까지 백업을 미루지 않는다.

## 9. R7: 매입 준비와 상태 갱신

매입 검토 사건마다 구성 범위·가격·전략·금융·임대차·규제·실사·협상안을 묶어 표시한다. 체크리스트의 세부 조건은 데이터 사전 §11을 따른다. 필수 검토·출처·검토일·유효성을 표시하고 미완료 상태에서 purchase_ready 전환을 막는다.

인수: 만료된 은행 검토, 미확인 보증금 명세, 바뀐 매입 범위, 미해결 명도 조건이 남으면 준비 완료가 되지 않는다. 중요한 입력이 변경되면 영향받은 검토를 다시 요구하고 과거 승인 이력을 보존한다.

계약 전·잔금 전 재확인 작업과 비교자료 내보내기를 제공한다. 계약·대출·납세의 법적 판단이나 실제 자금집행은 자동화하지 않는다. 실사·법률·세무 비용과 소요기간은 개발 공수와 구분한다.

## 11. 공통 검증과 운영

R1에서 유지할 최소 검증: 동일 ID·동일 내용 재반영 방지, 동일 ID·상이 내용 거절, 저장 실패 오표시 방지, 데이터 교체 시 미반영 기록 보존, 파일 무결성·ZIP 보안, DB 트랜잭션, 실제 폰 시험, 독립 사본.

R2 이후 추가: FK 타입 불일치, 정본/파생본 버전 차이, 점포 표본 변경·조사 누락, 부동산 원본 중복·취소·마스킹, 과거 지식 시점, 대지 제약·FAR 면적, 보증금과 대출의 중복 공제, 구매 준비 유효성.

코드 테스트는 GitHub Actions에서 가상자료만 사용한다. 실제 정본·사진을 runner에 올리지 않는다. API 수집은 PC에서 수동 실행으로 검증하고 안정화 후 로컬 예약 작업을 검토한다. PC가 꺼져 있으면 수집이 진행되지 않는다는 사실을 마지막 성공일로 표시한다.

성능 기준은 실제 폰의 선택 반응·저장시간·ZIP 크기·메모리로 측정한다. 배경 필지 3,000개는 시험값, 관찰목록 30~50개는 운영 목표다. 둘을 같은 한도로 사용하지 않는다. 한 번의 관측은 약 3분 이내를 목표로 하며 불필요한 필수 입력을 늘리지 않는다.

임장 직후 파일 내보내기·외부 사본, PC 정리 시 반영·백업, 월별 최근 거래, 분기별 관찰목록·표본 점검, 반기 복구·기기 시험, 연간 누적 재검증·보존본을 기본 주기로 둔다. 실제 부담을 기록해 주기를 조정한다.

## 12. 첫 코드 요청 범위

> 실제 저장소와 기존 지침을 읽고 환경·충돌 사항을 보고한다. J5-001~004에 해당하는 문서·설정·관측 스키마·가상자료·기기 시험용 최소 파일 흐름부터 구현한다. 새로운 실제 데이터 수집, 실사진 공개 업로드, 유료 서비스, 실제 배포는 승인 없이 수행하지 않는다. 지도·정본·복구 전체를 첫 PR의 완료조건으로 묶지 않는다.
