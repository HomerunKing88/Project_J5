# J5-010 단방향 반영

기록일: 2026-09-23.

## 결과

- `j5/db/schema.py` db_schema 2: `import_runs`(패키지 이름·sha256·package_id·판정·건수·dataset_version 전후·검사 보고 JSON), `import_events`(run 별 event_id·해시·고정 행 바이트·판정·record_id). `import_events` 의 `inserted` 행에 부분 UNIQUE 인덱스를 두어 이벤트 대장으로 쓴다(event_id 는 한 번만 반영). `import_events.run_id` FK 는 DEFERRABLE(수입 기록 행을 배치 끝에 넣는다).
- `j5/db/importer.py` `import_package(db, path, data_home)`: (1) `j5 inspect` 와 같은 검사(정본 물건 목록을 시드로, meta.study_id 비교, data_mode 비교) → 거절/보류, (2) 같은 파일(sha256) 재입력 → duplicate, (3) 이벤트 행·해시를 대장과 대조: 같은 ID·다른 해시 → held, 같은 해시 → 건너뜀, 정정 대상이 정본에도 패키지에도 없으면 held, 새 이벤트 없음 → duplicate(버전 유지), (4) 새 이벤트가 참조한 사진만 `photos/<sha[:2]>/<sha>.<ext>` 에 `.part`+fsync+재검증+`os.replace` 로 보관(같은 내용 있으면 재사용, 다른 내용이면 실패·손대지 않음), (5) 한 트랜잭션으로 출처 문서(패키지)·records·record_evidence·attachments·import_events·import_runs·`dataset_version` +1. 실패 시 롤백하고 보관한 사진은 정리대기로 결과·수입 기록·로그(`logs/import.log`)에 남긴다. 입력 파일은 어느 경우에도 바꾸지 않는다.
- CLI `j5 db import <package> [--data-home] [--json]`. 종료 코드 0 applied·duplicate / 1 rejected·failed / 2 held / 3 사용 오류.
- 테스트 `tests/test_j5_010_import.py` 17건: 정상(폴더·ZIP, 기록·사진·근거·대장·로그·원본 불변), 같은 파일 두 번, 재내보내기(다른 package_id·행 순서 변경), 일부 겹침, 패키지 안 같은 바이트 반복, 같은 ID·다른 내용(패키지 안·정본 대조), 거절 4종·study_id·data_mode·빈 정본, 정정 대상 없음 → 대상 반영 후 정정, 패키지 안 순서 무관 정정, 사진 복사 후 DB 실패(롤백·정리대기·재시도 재사용), 파일 실패, 기존 사진 내용 충돌, 패키지 해시 안정성, CLI.

## 데이터 사전에 없어 정한 값

- 판정 5종 `applied / duplicate / held / rejected / failed`. 거절·보류·중복·실패도 `import_runs` 에 기록한다(정본 데이터가 아니라 수입 로그이므로 `dataset_version` 은 그대로).
- 사진 보관 경로 `photos/<sha256 앞 2자>/<sha256>.<ext>`(J5_DATA_HOME 기준 상대경로). 내용 해시가 이름이라 여러 이벤트·패키지가 같은 파일을 공유한다.
- 패키지 식별은 ZIP 파일 바이트의 sha256, 풀어 놓은 폴더는 항목 이름·내용 해시 목록의 sha256.
- 출처 문서: 패키지마다 `source_documents` 한 행(`document_kind=field_package`, `document_id = uuid5(패키지 sha256)`, `collected_at = manifest.created_at`, `location` 은 데이터 홈 안이면 상대경로·아니면 파일명). 각 기록의 루트 근거(`$`)를 이 문서에 연결하고 locator 는 `observations.jsonl#event_id=…`.
- 기록 매핑: `event_id → record_id`, `asset_id → subject_id(asset)`, `corrects_event_id → supersedes_id`, `records.collected_at = manifest.created_at`, `source_kind = field_observation`, `schema_version` 은 payload 스키마 버전. 첨부 ID 는 `uuid5(event_id:sha256)`.
- 이벤트의 `route_version_id`·`frame_version_id` 는 records 열이 없어 대장의 고정 행 바이트에만 보존한다. R2(J5-013)에서 경로·표본 테이블과 함께 열을 둔다.
- 정정 대상이 없는 패키지는 보류한다(거절 아님). 대상이 담긴 패키지를 먼저 반영하면 통과한다. 같은 패키지 안에서는 대상을 먼저 넣는다(순환은 실패).
- 정리대기 사진은 결과·`import_runs.report_json`·로그에 경로를 남기고 자동 삭제하지 않는다. 정리 명령은 두지 않았다(사용자가 목록을 보고 처리).

## 공수

- 예상 8~12시간. 실제(세션 기준) 약 1시간. 재작업: `import_events.run_id` FK 가 즉시 검사되어 수입 기록 행보다 먼저 넣을 수 없었던 문제(DEFERRABLE 로 해결).

## 미확인 변수·남은 인수조건

- 실제 폰 ZIP 반영과 "실제 두 차례 임장 후 사용성"은 실기기 시험 이후(J5-012).
- R1b 인수 중 "DB 반영 후 파생본 실패"는 J5-011, "백업 실패"는 J5-012에서 시험한다.
- 사진 방향·썸네일·메타데이터 제거(§3.3 "R1b에서 검증")는 이 작업에 넣지 않았다. 원본 바이트를 그대로 보관한다.
- `import.log` 는 JSON 행 추가만 하며 회전하지 않는다.
