# J5-014 거래·2006년 소급·비교 깊이

기록일: 2026-09-23. 이 작업은 조각으로 나눈다. **A**(이 기록): 실거래 API 표본 월 수집 도구(R0 통과조건 실측). **B 이후**(별도): 실제 응답으로 확인한 필드로 거래 원본·정규화·범위·연결(데이터 사전 §7.2, R3).

## 데이터 사전에 없어 정한 값

- 원본 경로 `raw/rt_nrg/<시군구 5자리>/<YYYYMM>/p<페이지 3자리>-<실행 ID>.xml`. 실행 ID 는 UTC 시각 `YYYYMMDD-HHMMSS`. 같은 월을 다시 받으면 새 실행 ID 의 파일이 옆에 쌓인다(덮어쓰지 않음). `collection_runs` 정본 테이블은 R3 에서 만들고, 지금은 파일 기록이 체크포인트다.
- 기본 엔드포인트 `https://apis.data.go.kr/1613000/RTMSDataSvcNrgTrade/getRTMSDataSvcNrgTrade` 는 알려진 최신 주소를 코드에 적은 것이며 실제 응답으로 확인하기 전까지 가정이다. 사용자가 API 상세 페이지의 주소와 대조해 다르면 `--endpoint` 로 준다. 실제 쓴 주소는 기록에 남는다.
- 페이지당 1000행, 월당 최대 50페이지(옵션). 페이지 사이 0.2초 대기. `totalCount` 를 채우기 전에 빈 페이지가 오면 `partial`.

## 리뷰 반영 (PR #43, Codex 4건)

- P1 실행 ID 충돌: 실행 ID 를 UTC 초 시각 + 무작위 6자리로 만들고, 원본·기록·요약 파일은 배타적 생성(`open(…, "xb")`)으로만 써서 같은 이름이면 실패한다(덮어쓰기 없음).
- P1 재요약 범위: `rt-report` 는 월마다 한 실행만 센다(`--run-id` 또는 가장 최근 실행). 다른 실행 목록은 `other_runs` 로 표시한다. 여러 실행을 합치지 않는다.
- P1 되비친 URL: 응답 앞부분을 담는 오류 문구·resultMsg 를 결과 객체에 넣기 전에 가리고, CLI 출력도 한 번 더 가린다.
- P2 totalCount 없음: 항목이 있어도 `totalCount` 가 없거나 숫자가 아니면 `complete` 가 아니라 `partial`(완전성 확인 불가)로 둔다.

## R0 통과조건 판정

- **통과.** 최근·중간·2006년 표본 월 3개의 API 응답을 실측했다. 시군구 월 38~45행, 월 1페이지, 응답 0.1초 이내. 2006-01~2026-09 소급은 약 249회 호출로 일일 트래픽 안이다.
- 주소 공개 수준: 일반건축물 지번은 전 시기 마스킹, 집합건물 지번은 최근 월에서 공개(시점 미확인). 마스킹 행은 법정동+지번 앞자리 범위로만 좁히고 특정 PNU 로 확정하지 않는다.
- 연결 검토 대상 규모: 매입 검토 단위 기준 연 25~45건으로 릴리스 계획 §4 의 "연 30건 내외" 경계에 있다. **R3 의 연결 검토 화면은 만들지 않고 CLI 가 내는 CSV 후보 목록과 수동 확인(연결 명령)으로 대체한다.** 실제 운영에서 수동 확인 부담이 확인되면 새 ADR 로 화면을 검토한다.
- R3 공수 조정: 검토 화면 제외로 40~64시간에서 **32~48시간** 으로 낮춘다(릴리스 계획 §7 에 기록). 남은 위험은 집합건물 지번 공개 시점, 취소·정정의 실제 변경량, 2006~2010 구간의 필드 채움이다.

## B-1. 정본 거래 원본·정규화·수집 기록 (2026-09-25)

- db_schema 6 `r3_transactions`: `collection_runs`(실행×시군구×계약월: 결과·totalCount·항목·페이지 수·실행 기록 경로·출처 문서)·`collection_pages`(페이지별 결과·HTTP·resultCode·원본 경로·sha256·필드 채움 수)·`transaction_observations`(응답 항목 행을 태그명→문자열 그대로, 불변 트리거)·`transactions`(정규화, 아래 정체성 규칙). 연결 테이블(`transaction_links`)·검토 결정은 B-2.
- `j5 collect rt-fetch --from --to`: 계약월 범위를 받되 실행 기록 파일에서 complete/empty 인 달은 건너뛴다(`--refresh` 로 다시 받음: 취소·정정 점검). 체크포인트는 실행 기록 파일이다. 정본에는 쓰지 않는다.
- `j5 db rt-load`: 정본에 없는 실행 기록을 오래된 순으로 모두(또는 `--run-id`) 반영한다. 원본 XML 의 sha256 이 기록과 다르면 거절, 항목 수가 다르면 거절, 기록 형식이 깨졌거나 경로가 실데이터 홈 밖이면 거절. 같은 실행은 두 번 반영하지 않는다. 실제 제공자(apis.data.go.kr) 응답은 `private_real` 정본에만 넣는다. 한 실행은 한 트랜잭션이며 반영한 실행은 `source_documents`(official_api) 에 남는다.
- `j5 db rt-coverage --from --to`: 월별 수집 결과(complete/empty/partial/failed/none)·실행 횟수·거래·취소·사라짐·마스킹·연결 수. 수집 완료와 물건 연결 완료를 따로 센다(릴리스 계획 §7 인수조건).
- 테스트 `tests/test_j5_014b_transactions_db.py` 6건: 스키마·상태, 정규화(금액 만원→원, 계약일, 지번 마스킹·앞자리, 일반/집합, 지분, 취소일 `YY.MM.DD`, 결측 사유), 반영(수집 기록·페이지·원본 행 불변·같은 값의 별개 행 순번), 재수집(다시 확인·취소 갱신·사라짐·신규·부분 응답에서는 사라짐 표시 안 함·오래된 실행), 거절 시 정본 무변화(해시 불일치·손상 기록·경로 탈출·원본 없음·data_mode), 범위 현황·rt-fetch 건너뛰기·CLI·백업/복구 포함. 가상 서버만 쓴다.

### 데이터 사전에 없어 정한 값 (B-1)

- 거래 정체성 = (제공자, 시군구, 계약월, 식별 해시, 순번). 식별 해시 필드 15개: sggCd, umdNm, jibun, buildingAr, plottageAr, buildYear, dealYear/Month/Day, dealAmount, buildingType, buildingUse, landUse, floor, shareDealingType. 가변 필드(cdealType, cdealDay, dealingGbn, estateAgentSggNm, buyerGbn, slerGbn)는 뺀다. 실측에서 buyerGbn 등이 최근 월에만 채워지므로 이 필드가 나중에 채워져도 같은 거래로 본다.
- 같은 응답 안에서 식별 필드가 완전히 같은 행은 순번 0, 1, … 로 별개 거래다(데이터 사전 §7.2 "같은 값의 별개 행을 합치지 않는다").
- 같은 달의 새 실행(실행 ID 가 더 큰 것): 다시 보인 거래는 `last_seen_run_id`·가변 열 갱신, 완전한 응답(complete/empty)에서 안 보인 거래는 `missing_since_run_id` 만 적는다. 부분 응답에서는 표시하지 않는다. 취소는 `cdealType` 이 `O/Y` 일 때만 `cancelled`. 더 오래된 실행을 나중에 반영하면 새 거래만 넣고 `first_seen_run_id` 만 앞당긴다. 실행 순서는 실행 ID 문자열(UTC 초 시각) 순이며 같은 초의 실행은 접미사 순이다(실제 실행은 초 단위로 겹치지 않는다).
- 금액 `dealAmount` 는 만원 단위 문자열이라 ×10,000 으로 `amount_krw`(원). 해석 불가는 null + `missing_reasons_json` 사유(`not_provided`/`unparsable`). 면적·건축년도·계약일·취소일도 같다.
- 초기 범위 `scope`: 지분 거래 → `partial_share`, 집합건물 → `strata_unit`, 그 외 `unclear` (`scope_basis=auto_provider_fields`). `whole_asset` 은 자동으로 주지 않는다. `link_status` 는 B-1 에서 `unlinked` 만 쓴다.
- 취소일 `YY.MM.DD` 는 20YY 로 해석한다(자료 시작이 2006년).

## 공수

- 예상(J5-014 전체) 32~48시간(R0 실측 후 조정). A 실제(세션 기준) 약 1시간, 리뷰 반영·실측 지원·후속 보완 약 1시간. 사용자 실측(키 설정 포함) 약 40분. B-1 실제 약 2시간.

## 미확인 변수·남은 인수조건

- 실제 API: 엔드포인트·필드·2006년 응답·월당 페이지 수·법정동별 행수·거래 범위 분포는 실측 3·4차로 확인됐다. 남은 것은 집합건물 지번 공개 시점(표본 두 달 추가)과 핵심 범위의 중심·반경 지정이다.

- B-2 이후: `transaction_links`·검토 결정(후보 CSV → 수동 연결·철회), 비교 블록 분류, 취소·정정 점검 주기(월 1회 최근 6개월 `--refresh`), 파생본·폰 표시.
- B-1 은 가상 서버로만 검증했다. 실제 반영은 사용자 PC 에서 `rt-fetch` → `rt-load` → `rt-coverage` 로 확인한다. 실측 원본 3개월(실행 20260923-215249-cc7db5)이 첫 대상이다.
