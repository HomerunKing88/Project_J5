# J5-039 정본 필지 상한과 폰 파생본 범위 분리 (ADR-23)

기록일: 2026-09-28. 정본의 필지 상한은 폰 파생본과 같은 8,000 이었다(J5-013B-2 리뷰 반영: 파생본이 영영 실패하지 않게 반영 전에 막음). 비교 지역을 더하면 이 상한에 닿아 정본 반영이 거절되고 PC 조회도 막힌다. 사용자 결정(2026-09-28)으로 정본 상한은 풀고, 폰에 실을 필지 범위를 따로 정하기로 했다.

## 결과

- `j5/db/parcels.py`:
  - `CANONICAL_MAX_PARCELS = 100_000`. `load_bundle` 의 합계 검사가 이 값을 쓴다.
  - `phone_scope`·`set_phone_scope`·`scope_overview`·`scope_text`. 범위는 meta `phone_parcel_scope` 에 둔다. 정본에 없는 법정동 코드·10자리가 아닌 코드는 거절한다. 범위가 바뀌면 dataset_version 을 올린다(리뷰 반영, 아래).
  - `parcels_bundle_from_db` 는 범위를 정했으면 그 법정동의 필지와, 파생본 생성일에 유효한 물건 연결이 있는 필지만 싣는다. warnings 에 "폰 범위: 정본 필지 N개 중 …" 을 적는다.
- `j5/db/projection.py`: 실릴 필지가 폰 상한(`MAX_FEATURES` 8,000)을 넘으면 `parcels_phone_limit` 으로 실패한다. 이전 파생본은 그대로 두고 `db phone-scope` 로 범위를 정하라고 안내한다.
- CLI `db phone-scope [--emd …] [--all] [--json]`: 인자가 없으면 법정동별 필지 수와 폰에 실릴 수를 보인다.
- 폰 `web/app/main.js`: 필지 안내가 "폰 범위:" 경고는 글 그대로, 다른 경고는 건수로 보인다. 앱 0.2.14, SW 캐시 v0.2.14.
- 문서:
  - ADR-23(새), 데이터 사전 §2 meta `phone_parcel_scope`, 릴리스 계획 §10 J5-039.
  - `j5/README.md`·`web/README.md`·`tests/README.md`, 색인(J5-037 #84·#85, J5-038 #85).
- 시험:
  - `tests/test_j5_039_phone_scope.py` 4건을 새로 썼다.
  - `tests/test_j5_013b2_parcels_db.py` 의 합계 상한 시험은 정본 상한 상수를 보도록 고쳤다. 결정이 바뀐 것이며 검사는 그대로 남긴다.
  - e2e 필지 안내에 폰 범위 경고 확인을 더했다.
- J5-038 자체 검토 반영: 같은 PNU 가 여러 번 오면 한 필지에 물건이 둘 생기던 것을 막았다(작업 기록 J5-038).

## 리뷰 반영 (PR #86, Codex 3건)

- P2 실패 기록의 버전: 폰 상한 검사가 스냅샷을 읽는 중에 일어나 결과·실행 기록에 정본 버전이 0 으로 남았다. 검사를 버전을 적은 뒤로 옮겼다.
- P2 범위 변경 뒤의 옛 파생본·백업: 범위를 바꿔도 dataset_version 이 그대로라, 이전 범위의 파생본과 백업이 최신으로 표시됐다. 범위가 실제로 바뀌면 dataset_version 을 올리고, 같은 범위면 바꾸지 않는다. ADR-23 과 데이터 사전의 "올리지 않는다" 를 고쳤다.
- P2 범위 밖 출처: 필지를 걸러도 `attrs_sources` 는 정본 전체의 출처를 모아, 실지 않은 지역의 출처가 적히고 출처가 많으면 번들 스키마(60개)를 넘을 수 있었다. 실은 필지의 속성·출처만 모은다.
- 시험 보강: 버전 오름·같은 범위 그대로·이전 파생본 구본, 옆 동만 범위일 때 출처, 실패 기록 버전. 고치기 전 코드에서 실패함을 확인했다.

## 데이터 사전에 없어 정한 값

- 정본 상한 100,000. 폭주 방지용 상한이며 성능 실측 값은 아니다.
- 범위 단위는 법정동 코드 10자리(`parcels.emd_code`)다. 물건이 연결된 필지는 범위와 무관하게 싣는다.

## 미확인 변수

- 정본 필지가 수만 개일 때 `parcels-find`·`project`·`phone-scope` 의 실행 시간을 재지 않았다. 필지마다 위치점 포함 검사를 하는 부분(`assets_by_parcel`)이 가장 느릴 것으로 본다.
- VWorld 한 구역 묶음이 8,000필지(번들 스키마 상한)를 넘는 경우는 이번에 다루지 않았다. 종로 3구역은 구역마다 1,500필지 이하였다.

## 남은 인수조건·후속 작업

- 사용자(PC): 비교 지역 VWorld 자료를 `db parcels-ingest` 로 더한 뒤 `db phone-scope` 로 법정동별 수를 보고, `--emd` 로 핵심 법정동을 정한다. `project` → `project-copy` 뒤 폰 필지 안내에 "폰 범위" 가 보이는지 확인한다.
