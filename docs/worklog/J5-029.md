# J5-029 관심 단계·관찰목록 관리

기록일: 2026-09-27. 필지 수천 개·속성·검색·기기 물건이 폰에 들어온 뒤, 현장에서 다시 볼 물건(관찰목록)을 배경 목록과 나눌 길이 없었다. 정본에는 관심 단계 8종이 있었지만 바꾸는 명령은 매입 준비 승인·철회뿐이었고, 파생본 `assets.geojson` 에 실린 단계를 폰은 읽지 않았다. 릴리스 계획 §8 R2 "배경 목록과 30~50개 정기 관찰목록을 구분" 을 ADR-22 로 채택해 구현했다. 가상자료만 썼다.

## 결과

- 정본(`j5/db/schema.py` 마이그레이션 17 `tracking_changes`): 물건·이전 단계·새 단계·변경일·사유·출처(`asset_track`/`readiness`)·준비 결정 ID 의 불변 표(UPDATE·DELETE 거절). 기존 `readiness_decisions` 를 백필한다. `db status` 행 수에 `tracking_changes`.
- `j5/db/tracking.py`(새): `set_status`(같은 트랜잭션에서 단계 갱신 + 이력 행 + dataset_version, purchase_ready 로/에서는 거절, hold·excluded·archived 는 사유 필수, 같은 단계는 변경 없음), `history`, `overview`(단계별 수·pending 수·관찰목록 `watch`·`detailed_review`·`purchase_ready` 와 마지막 변경일, 50개 초과 경고 문구), 텍스트 출력. `j5/db/readiness.py` 의 승인·철회가 같은 이력 표에 `decision_id` 와 함께 남긴다.
- CLI(`j5/cli.py`): `db asset-track <asset_id> [단계] [--reason] [--on] [--json]`(단계 생략 시 이력), `db watchlist [--json]`.
- 파생본(`j5/db/projection.py`, `schemas/assets_seed.schema.json`): 시드 물건마다 `tracking_status`·`resolution_status`(선택, 열거값). `db load-seed`(`store.py`)는 이 필드가 든 시드를 거절한다.
- 폰(`web/app/seed.js`·`main.js`·`index.html`·`styles.css`): 시드 검증에 두 필드 허용값, 단계 이름표·관찰목록 정의·`filterAssets`. 목록 카드와 지도 선택 카드에 단계 배지(미검토는 없음, 관찰목록 단계 강조, 보류·제외·보관 흐림)와 "확인 전 · PC 에서 확정" 배지(pending). 대상 목록 위 "전체/관찰목록만" 필터(관심 단계가 있는 시드에서만 보임, 선택은 meta `asset_filter`)가 목록·지도 점·"관측 시작"의 다음 대상에 같이 적용된다. 관찰목록이 비면 안내 문구. 자료 관리 상태에 "관찰목록 N개". 단계를 바꾸는 버튼은 없다. 앱 0.2.8, SW 캐시 v0.2.8.
- fixture: `tests/fixtures/make_view.py` 가 관심 단계 4건(관찰·상세 검토·보류·제외)을 넣은 파생본을 만든다.
- 테스트: `tests/test_j5_029_tracking.py`(8건), `tests/web/seed.test.mjs` 1건, `app.e2e.test.mjs` 관심 단계·필터·재접속 유지·관측 시작 절. 마이그레이션 번호를 참조하는 시험 5곳 갱신(018b 는 버전 13 정본의 승인을 직접 SQL 로 흉내내 백필까지 확인).
- 문서: ADR-22, 릴리스 계획 §10 J5-029, 데이터 사전 §2(tracking_changes·시드 출력 필드), `j5/README.md`·`web/README.md`·`schemas/README.md`·`tests/README.md`, 색인(J5-028 PR #74).

## 데이터 사전에 없어 정한 값

- 관찰목록 = `watch`·`detailed_review`·`purchase_ready`. `hold` 는 관찰목록 밖(보류), `background`·`unreviewed` 는 배경, `excluded`·`archived` 는 제외. 폰 필터와 `db watchlist` 가 같은 정의를 쓴다.
- 사유 필수 단계: `hold`·`excluded`·`archived`(관찰에서 빼는 결정). 다른 단계는 사유 선택.
- `asset-track` 의 purchase_ready 거절(전환·이탈 모두 readiness 명령). 준비 결정을 같은 이력 표에 두고 백필하는 것.
- 폰 배지 이름표(미검토·배경·관찰·상세 검토·매입 준비·보류·제외·보관)와 "확인 전 · PC 에서 확정" 문구. 미검토는 배지 없음.
- 필터 선택은 기기 meta `asset_filter` 에 남고, 관심 단계 없는 시드(수동 시드·연습 자료)에서는 필터를 숨기고 전체를 보인다(저장값은 유지).

## 미확인 변수

- 실제 정본의 마이그레이션 17 은 사용자 PC 에서 백업 뒤 `db status` 로 확인한다. 준비 결정이 있는 정본이면 백필 행 수가 결정 수와 같아야 한다.
- 관심 단계의 실제 운영 기준(언제 watch 로 올리고 언제 hold 로 내리는지)은 사용자가 정한다. 도구는 사유를 남길 뿐 판단하지 않는다.
- iPhone 실기기에서 필터 버튼(aria-pressed 강조)·배지 가독성은 실사용 확인 항목이다.

## 남은 인수조건·후속 작업

- 사용자(Mac): 실데이터 홈에서 `backup` → `j5 db status`(마이그레이션 17) → 실제 물건에 `db asset-track <asset_id> watch --reason ...` → `db watchlist` → `project` → `project-copy` → 폰에 넣고 배지·"관찰목록만" 확인.
- 후속 후보: 폰 필지 패널의 "안의 물건" 에 단계 표시, 관찰목록 물건만 내보내기 요약, 정기 점검 주기(분기별 관찰목록 점검)의 체크리스트.
- 가상자료·브라우저 통과는 실제 기기·법률 검증이 아니다.
