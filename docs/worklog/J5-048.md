# J5-048 범위 규칙의 시군구

기록일: 2026-09-28. 거래 범위 규칙(J5-014B-3)은 법정동 이름 목록으로 핵심·비교를 정했다. ADR-23 부터 정본에 여러 지역을 넣으므로, 다른 시군구의 같은 이름 법정동 거래가 핵심 범위로 분류될 수 있었다. 지번 대조에서 고친 문제(J5-044)와 같은 종류다.

## 결과

- 규칙 파일(`schemas/zone_rules.schema.json`)에 선택 항목 `lawd_cd`(시군구 5자리 또는 null)를 더했다.
  - 주면 그 시군구의 거래만 핵심·비교로 분류하고, 다른 시군구의 같은 이름 법정동은 범위 밖(outside)으로 둔다.
  - 없으면 이전처럼 이름으로만 본다. 기존 규칙과 기존 정본은 그대로 동작한다.
- `j5/db/zones.py`
  - `classify(rules, emd_name, lawd_cd)`: 규칙에 시군구가 있으면 거래 시군구가 다를 때 범위 밖이다.
  - `apply_rules`: 모든 거래를 시군구와 함께 다시 분류한다. 시군구만 바뀌어도 새 규칙 판이 된다. 시군구가 없는 규칙은 저장 형식(`rules_json`)이 이전과 같다.
  - `current_rules` 가 `lawd_cd` 를 돌려주고, `rt-zones show` 글에 "시군구: 11110 만 / 정하지 않음" 줄이 생긴다.
  - `rt-load`(`transactions.load_run`)도 새 거래를 시군구와 함께 분류한다.
- 파생본 `transactions.json` 의 `zone_rule` 에 `lawd_cd` 를 싣는다(없으면 null). 게시 전 확인과 폰 검증이 형식(5자리 숫자 또는 null)을 검사한다.
- 폰 `parcelYearSummary`: 규칙에 시군구가 있고 필지 시군구(PNU 앞 5자리)와 다르면 이름이 같아도 범위 밖으로 보인다(PC `classify` 와 같다). 앱 0.2.18, 캐시 v0.2.18.
- 시험
  - `tests/test_j5_048_zone_sgg.py` 4건: 반영 시 재분류와 새 거래 분류에서 다른 시군구의 같은 이름 동은 범위 밖, 시군구 없는 규칙은 이름으로만, 시군구만 바뀌어도 새 판·같으면 변화 없음, 형식 오류 거절, 규칙 글, 파생본의 `lawd_cd` 와 범위 밖 거래 제외, 해시를 맞춘 변조 거절. 고치기 전 코드에서 3건이 실패함을 확인했다. 나머지 1건(잘못된 시군구 거절)은 이전 스키마도 모르는 키로 거절한다.
  - `tests/web/view.test.mjs`: 규칙 시군구 형식 검사와 범위 판단. 고치기 전 코드에서 실패함을 확인했다.
  - J5-047 시험의 `zone_rule` 기대값에 `lawd_cd: null` 을 더했다.
- 문서: 릴리스 계획 §10 J5-048, `j5/README.md`, `web/README.md`, `tests/README.md`, 색인(J5-047 #94).

## 데이터 사전에 없어 정한 값

- 규칙 하나에 시군구 하나다. 여러 시군구에 걸친 핵심·비교 범위는 지금 규칙 형식으로 나타낼 수 없다. 필요해지면 법정동마다 시군구를 적는 형식을 새 작업으로 검토한다.
- 시군구 코드는 거래의 `lawd_cd`(수집 요청 시군구)로 본다(J5-044 와 같다).

## 미확인 변수

- 사용자의 실데이터 규칙에는 시군구가 없다. 종로구만 모으는 동안은 결과가 같다. 다른 시군구를 모으기 전에 규칙에 `lawd_cd` 를 넣어 새 판으로 반영해야 한다.

## 남은 인수조건·후속 작업

- 사용자(PC): 규칙 파일에 `"lawd_cd": "11110"` 을 넣고 `j5 db rt-zones apply <규칙.json>` → `rt-zones show` 로 "시군구: 11110 만" 을 확인한다. 반영하면 dataset_version 이 올라가므로 `backup` → `project` 를 다시 한다.

각 명령의 세부는 `j5/README.md`.
