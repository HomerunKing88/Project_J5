# J5-007 고정 이벤트·ZIP 내보내기

기록일: 2026-09-22.

## 결과

- `web/app/zip.js`: STORED 전용 ZIP 작성기(ADR-11). CRC32(node zlib 대조), DOS 시각, UTF-8 이름 플래그, 연속 배치. Python `zipfile.testzip()`·`j5 inspect`로 검증.
- `web/app/export.js`: 대상 선택(기록의 study_id·data_mode = 현재 설정, 기본 미내보냄만), 저장 순서 first-fit 묶음 나누기(ZIP 100MB·해제 250MB·사진 1000장·observations.jsonl 20MB), manifest 생성, 사진 재검증(크기·sha256) 후 패키지 Blob 생성. 행 바이트는 `record.line` 그대로.
- `web/app/db.js`: `listEventsFor`, `getPhotos`, `photoMeta`, `appendExport`, `markExported`(events+meta 한 트랜잭션). DB 버전 유지.
- 화면: 내보내기 절(대상·사진·예상 크기·묶음 수, 제외 사유, 묶음 준비 → 파일 저장 k/n → 파일 저장 확인, 이력). 다운로드는 클릭 핸들러 안에서 동기 실행.
- e2e: 관측 저장 → 묶음 준비 → 실제 마우스 클릭으로 다운로드 → `j5 inspect` ok(zip, events 1, photos_referenced 1) → 확인 전 `저장됨` 유지 → 확인 후 `내보냄` → 내보낸 기록 포함 재내보내기 ZIP의 observations.jsonl 해시 동일, package_id 상이 → 미확인 시도는 `exported_in`에 안 들어감.

## 데이터 사전에 없어 정한 값

- `meta.exports[]`: `{package_id, created_at, filename, study_id, data_mode, event_ids, photo_count, bytes, confirmed_at}`. 파일 저장 버튼 시점에 추가, 확인 시 `confirmed_at`.
- 두 단계 확인: 다운로드는 상태를 바꾸지 않고 "파일 저장 확인"이 `saved → exported`로 바꾼다(ADR-02의 `내보냄` 정의).
- 파일명 `<study_id 정제>-<YYYYMMDD-HHMMSS>-<k>of<n>-<package_id 앞 8자>.j5field.zip`.
- 묶음 간 공유 사진은 각 묶음에 중복 포함(내용 해시 이름이라 PC에서 동일 파일).
- `photos/` 디렉터리 항목은 넣지 않는다. 항목 순서: manifest.json, observations.jsonl, 사진 이름순.

## 공수

- 예상 8~12시간. 실제(세션 기준) 약 2시간. 재작업: 테스트 시나리오 기대값 2회 수정(같은 묶음 안의 공유 사진은 한 번만 센다).

## 미확인 변수·남은 인수조건

- iPhone Safari 실기기(2026-09-23, iOS 18.7, J5-004 기록): a[download] 는 '파일' 앱에 저장되고 "파일 저장 확인" 뒤 `내보냄` 배지가 붙는다. PC `j5 inspect` ok. 홈화면 모드·100MB 급 Blob 은 미확인.
- 비보안 컨텍스트에서는 순수 JS sha256으로 사진을 다시 해시하므로 큰 묶음은 느릴 수 있다.
- 완료 조건 "재내보내기 안정성"은 e2e로, "자동 삭제 없음"은 코드 경로(삭제 API 없음)로 확인했다. 실제 두 차례 임장 후 사용성 확인은 J5-012에서.
