# J5-017 이전·휴면 운영 (R6)

기록일: 2026-09-26. 첫 조각 **A**: 운영 점검·휴면 재개(`j5 db ops-check`)와 마지막 정상 버전 저장. 완료 조건 "새 기기·구버전·백업 재개"(릴리스 계획 §10)와 §8 R6 의 반기 운영 점검·정본·사진 복구·새 PC 이전·"마지막 정상 앱·DB·스키마·도구 버전을 저장한다" 를 다룬다. 둘째 조각 **B**: 연말 개방형 포맷 보존본(`j5 db archive`). 구패키지 열람, 외부 서비스 중단 대응, 폰(도메인) 이전 화면은 뒤 조각이다.

## A. 결과

- `Db.open_readonly(path)`: 정본을 `mode=ro` 로 연다. 마이그레이션을 적용하지 않으므로 도구보다 오래된 정본을 그대로 읽고, 도구보다 새로운 정본은 `tool_too_old` 로 거절한다(모르는 표·열을 해석하지 않는다). 쓰기 트랜잭션은 SQLite 가 거절한다. 기존 `Db.open` 의 동작(열 때 마이그레이션)은 바꾸지 않았다.
- `j5 db ops-check [--data-home] [--json]`(`j5/db/ops.py`): 읽기 전용 점검. 도구·정본 db_schema 와 대기 마이그레이션 목록, `integrity_check`·`foreign_key_check`, 백업 상태(기존 `backup_status`: 포인터·manifest 실제 확인)와 마지막 백업 경과일, 파생본 상태(`projection_status`), 사진 대사(`check_photos`)·수집 원본 대사(`check_raw_files`), 마지막 활동(반영 `import_runs`·수집 반영 `collection_runs`·파생본 게시 `projection_runs`·백업 포인터; 표가 없는 구버전 정본은 "표 없음" 으로 값 없음과 구분). 할 일을 순서대로 낸다: 도구 갱신(정본이 더 새로움) → 무결성·외래키 → 마이그레이션 대기(백업 확인 뒤 쓰기 명령으로 열어 적용, 그 뒤 다시 백업) → 백업 → 파생본 → 사진·원본 되찾기. 종료 코드 0 통과(할 일 없음) / 1 조치 필요 / 3 사용 오류. 정본·백업·파생본·사진을 바꾸지 않는다.
- 마지막 정상 상태 `J5_DATA_HOME/ops/last_known_good.json`(`format: j5lastgood`): 점검을 통과했을 때만 원자적으로 쓴다. 앱 버전(`j5 0.1.0`), 도구 db_schema 와 정본 db_schema, package·projection·backup 스키마 버전, SQLite·Python 버전·플랫폼, study_id·data_mode·dataset_version·행 수, 백업·파생본 위치·버전·시각. 통과하지 못하면 이전 파일을 그대로 두고 "마지막 정상 상태" 로 보여 준다. 읽을 수 없는 파일은 주의로 표시하고 다음 통과 때 다시 쓴다. 매 실행은 `logs/ops_check.log` 한 줄.
- 반기 점검 기한: 마지막 통과 점검(없으면 마지막 백업) 기준 180일 초과 시 `반기 점검 기한 초과` 표시. 조치 항목이 아니라 표시다.
- 운영 순서 문서화(`j5/README.md`): 휴면 재개(`ops-check` → 백업 확인 → 열어서 마이그레이션 → `backup` → `project` → `ops-check` 통과), 새 PC 이전(백업 폴더 → `restore` 빈 폴더 → `ops-check` 가 "백업 필요" 를 알림 → `backup`·`project` 재개 → 통과), 폰 이전(IndexedDB 는 origin 에 묶이므로 도메인·기기 변경 전 내보내기 → PC 반영 → 새 폰에 파생본 시드).
- 리뷰 반영(PR #56, Codex 3건): 백업이 최신으로 보이면 포인터·manifest 대조에 그치지 않고 백업 폴더를 전부 다시 읽어 검증한다(`verify_backup_dir`: 파일 해시·DB 사본·사진 연결). manifest 만 남고 사진·사본이 지워진 백업은 `손상 (백업 필요: 내용 검증 실패)` 이며 통과가 아니다. 마지막 정상 파일을 쓸 수 없으면(디스크·권한) 트레이스백 대신 조치 항목 `last_good_write_failed` 로 낸다. 통과한 점검의 결과는 방금 쓴 파일을 돌려주고 이전 점검 시각은 `previous_last_good_at` 으로 따로 둔다(기한 계산용).
- 테스트 `tests/test_j5_017a_ops.py` 8건: 할 일 목록 → 백업·파생본 뒤 통과·마지막 정상 파일 내용 → 반영 뒤 실패 시 이전 파일 유지; 구버전 정본(마지막 마이그레이션 행 삭제)은 대기 목록만 보고하고 파일을 바꾸지 않음·읽기 전용 쓰기 거절·쓰기 명령으로 열면 적용·도구보다 새로운 정본 거절; 사진 누락·정본 없음; 새 PC 이전(빈 폴더 복구 → 점검 → 백업 재개 → 통과, 옛 PC 파일 불변); 기한 초과·손상된 마지막 정상 파일; CLI.

## B. 결과 (연말 개방형 포맷 보존본)

- `j5 db archive [--dest] [--photos]`(`j5/db/archive.py`): 정본의 읽기 스냅샷(`Db.snapshot`) 안에서 모든 사용자 표를 읽어 `tables/<표>.jsonl`(행마다 JSON 객체, 열 순서는 표 정의, NULL 은 null, BLOB 은 `{"$hex": ...}`, JSON 열은 문자열 그대로: 정본 값을 그대로 보존)과 `tables/<표>.csv`(UTF-8, 헤더 1행, NULL 은 빈 칸)로 쓴다. `assets.geojson`(위치점 있는 물건, 없는 물건은 목록), `parcels.geojson`(필지가 있을 때, 폰 번들 형식), `schema.sql`(sqlite_master 의 표·인덱스·트리거 정의), `schemas/`(저장소 JSON Schema 13개 사본), `README.txt`(내용·한계 설명), `archive_manifest.json`(`schemas/archive_manifest.schema.json`: 파일 목록·해시, 표별 행 수·열 정의, 도구·SQLite·Python 버전). `--photos` 면 첨부가 참조한 사진을 해시 검증하며 복사하고 하나라도 없으면 실패다.
- 임시 폴더에 전량 쓰고 디스크에서 다시 읽어 검증(`verify_archive_dir`)한 뒤에만 `exports/private/archives/<stamp>-ds<버전>-<run8>/` 로 이름을 바꾼다. 실패하면 `failed-<run8>/` 에 남기고 정본·백업·파생본·이전 보존본은 그대로다. 포인터는 두지 않는다(보존본은 "최신" 개념이 없는 시점 스냅샷). `logs/archive.log` 한 줄.
- `j5 db archive-verify <폴더>`: 정본 없이 파일 해시·누락·여분, 표별 jsonl·csv 행 수·열, 사진 연결(`attachments` 표의 rel_path·sha256·bytes 와 대조), GeoJSON 버전·점 수, 필수 파일을 확인한다.
- 테스트 `tests/test_j5_017b_archive.py` 6건.

## 데이터 사전에 없어 정한 값

- "통과" 는 할 일이 없음이다: 무결성·외래키 정상, 도구·정본 스키마 같음, 백업 최신·접근 가능·내용 검증 통과, 파생본 최신, 참조 사진·수집 원본 전부 확인. 백업 내용 검증은 매번 전량 해시라 사진이 많으면 오래 걸린다(반기 점검이므로 허용, 실제 부담을 기록한 뒤 조정). 파생본 구본도 조치 항목이다(정본 기록이 없더라도 "재생성 필요").
- 마지막 정상 상태는 정본이 아니라 실데이터 홈의 파일이다(정본을 바꾸지 않으려고, 백업 포인터와 같은 원칙). 백업 대상에 넣지 않는다(복구 뒤 점검으로 다시 만든다).
- 반기 기한 180일은 릴리스 계획 §8 "반기 운영 점검" 을 날짜로 옮긴 값이다. 기한 초과는 표시만 한다.
- 정본이 도구보다 새로우면 점검도 열지 않는다. 모르는 스키마의 무결성을 "정상" 이라 말하지 않기 위해서다.
- 마이그레이션 적용은 점검 명령이 하지 않는다. 쓰기 명령(`j5 db status` 등)이 열 때 적용되며, 점검은 그 전에 백업 상태를 확인하라고 안내한다. 자동으로 백업을 만들지도 않는다(백업 위치·장치는 사용자가 정한다).
- 보존본의 CSV 는 편의 사본이다. CSV 는 NULL 과 빈 문자열을 구분하지 못하므로 정확한 값은 jsonl 이 정본 사본이다(README 와 매니페스트에 명시). 개방형 포맷 세 가지(CSV/JSONL/GeoJSON)를 모두 두되 우선순위는 jsonl 이다.
- 보존본은 표를 가공하지 않는다(payload_json 은 문자열 그대로, 정정 기록도 그대로). 읽기 좋은 형식은 파생본(`records.jsonl` 의 payload 객체)이 맡는다. 보존본의 목적은 도구가 없어도 원래 값을 되찾는 것이다.
- 보존본에 백업 원본(raw/)·파생본·로그는 넣지 않는다. 수집 원본은 백업이 보존하고, 정규화된 거래는 표로 들어간다.
- 폰 앱 버전은 마지막 정상 파일에 넣지 않았다. PC 도구가 폰의 앱 파일을 알 수 없고, 앱 캐시 이름(`sw.js` 의 `j5-app-v0.1.0`)은 폰에서만 확인된다. 필요가 확인되면 폰 화면에 표시하는 조각으로 둔다.

## 공수

- 예상(J5-017 전체): 릴리스 계획 R6 예산 12~20시간 범위. A 실제 약 1.5시간(리뷰 반영 포함), B 실제 약 1시간.

## 미확인 변수·남은 인수조건

- 실제 정본·외장 백업에서 `ops-check` 실행(휴면 재개 절차의 실사용). 외장 드라이브 미연결 시 `접근 불가` 표시는 가상 시험(폴더 이동)으로만 확인했다.
- 실제 새 PC 이전(다른 OS·경로·Python 버전)과 폰 도메인 이전은 실기기 항목이다. 폰 이전 전 미내보냄 기록 수를 폰 화면에서 확인하는 기능은 필요가 확인되면 별도 조각으로 둔다.
- 실제 정본으로 보존본을 만들어 외장 위치에 두고 `archive-verify` 로 확인하는 것은 실사용 항목이다. 보존본 크기(사진 포함)의 실제 부담을 기록한 뒤 주기를 조정한다.
- 남은 R6 항목: 구패키지·구파생본 열람(현재 package_schema 1.0.0 하나뿐이라 실제 구버전이 생길 때 검증), 외부 서비스 중단(공식 API 중단 시 마지막 성공일 표시는 `ops-check` 의 마지막 수집 반영일로 일부 다룸), 폰 이전 화면.
