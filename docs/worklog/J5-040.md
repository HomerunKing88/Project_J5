# J5-040 큰 VWorld 묶음 나눠 넣기

기록일: 2026-09-28. J5-039(ADR-23)로 정본은 여러 지역의 필지를 담을 수 있게 됐다. 그런데 번들 한 개의 상한은 폰 계약(스키마 `features` maxItems 8,000)과 같아서, 시군구 단위처럼 8,000필지를 넘는 VWorld 묶음은 `parcels-ingest` 의 변환 단계에서 `too_many_features` 로 거절됐다(J5-039 미확인 변수). 번들 계약은 그대로 두고, 묶음 넣기가 큰 입력을 번들 여러 개로 나눠 반영하게 했다.

## 결과

- `j5/parcels/convert.py`:
  - `ConvertOptions.split` 을 켜면 한 입력의 상한이 `SPLIT_MAX_FEATURES`(100,000)가 된다. 번들 상한을 넘는 결과는 전체 스키마 검증을 건너뛴다(조각마다 검증).
  - `split_bundle(bundle, size)`: PNU 순으로 size 개씩 나눈다. 조각마다 필지 수·범위를 다시 적고 "큰 묶음(N필지)을 나눈 번들 i/n" 경고를 더한 뒤 스키마를 검증한다. 출처·자르기 범위·속성 출처는 그대로 둔다.
  - `parcels convert`(나누지 않는 변환)의 상한과 동작은 그대로다.
- `j5/db/ingest.py`:
  - 변환을 나누기 모드로 하고 `PART_SIZE`(= 8,000)씩 나눈다. 나눈 번들은 `<이름>.partNNofMM.j5parcels.json` 이다. 나누지 않은 번들은 이전 이름 그대로라 이미 만든 번들을 다시 쓴다.
  - 다시 실행하면 조각 전부를 다시 쓴다(출처 표기 대조 포함). 조각이 일부만 있으면(중간에 끊긴 변환) `parts_incomplete` 로 거절하고 아무것도 반영하지 않는다.
  - 반영은 조각마다 `load_bundle` 트랜잭션이다. 입력 하나의 결과는 조각 합계와 조각 수(`parts`)다.
  - 결과 글에 "번들 N개로 나눔" 을 적는다.
- 시험 `tests/test_j5_040_split_ingest.py` 4건: 조각 크기를 4로 줄여 가상 6필지를 2조각으로 나눈다.
- 문서: 릴리스 계획 §10 J5-040, `j5/README.md`, `tests/README.md`, 색인(J5-038 #85·#86, J5-039 #86).

## 데이터 사전에 없어 정한 값

- 조각 크기는 번들 상한과 같은 8,000필지, 나누는 순서는 PNU 순, 조각 파일 이름은 `partNNofMM` 이다.
- 한 입력의 상한은 100,000필지(정본 상한과 같다)다.

## 테스트 명령과 결과 (2026-09-28, 컨테이너 Linux, Node 22, Python 3.11)

- `python -m pytest -W error::UserWarning` → 408 passed (새 시험 4건 포함).
- `node --test --test-timeout=180000 "tests/web/*.test.mjs"` → 폰 변경 없음.

## 실제 작업 시간

약 0.7시간 (확인 0.1, 구현 0.3, 시험 0.2, 문서 0.1).

## 미확인 변수

- 실제 시군구 단위 VWorld 자료(수만 필지)의 변환 시간·메모리를 재지 않았다. 변환은 한 입력을 메모리에 모두 읽은 뒤 나눈다.
- 조각 중간에서 반영이 실패하면 앞 조각은 남는다(묶음 넣기의 기존 규칙과 같다). 다시 실행하면 반영된 조각은 변화 없음으로 지나간다.

## 남은 인수조건·후속 작업

- 사용자(PC): 비교 지역의 시군구 단위 VWorld 자료를 `db parcels-ingest` 로 넣는다. 결과의 조각 수와 실행 시간을 기록하고, `db phone-scope` 로 폰 범위를 정한다.
