# J5-012 백업·복구·두 차례 실사용

기록일: 2026-09-23.

## 결과

- `j5/db/backup.py` `create_backup(db, data_home, dest_root=None)`: 정본 연결의 읽기 스냅샷(`Db.snapshot()`, BEGIN 지연 + 첫 읽기로 공유 잠금) 안에서 버전·행 수·첨부 목록을 읽고 같은 스냅샷을 SQLite 백업 API(`Connection.backup`)로 사본에 쓴다. 그동안 다른 연결의 쓰기는 커밋되지 않는다(데이터 사전 §12 "쓰기를 잠시 중단"). 사본을 읽기 전용(`mode=ro`)으로 열어 `integrity_check`·`foreign_key_check`·테이블별 행 수·meta 를 원본 스냅샷과 대조하고, 첨부가 참조한 사진을 내용 해시·크기를 검증하며 복사(fsync·재읽기)한 뒤 `backup_manifest.json` 을 쓴다. 디스크에서 전부 다시 읽어 검증(`verify_backup_dir`)한 뒤에만 최종 폴더로 이름을 바꾸고 `backups/latest.json` 포인터를 교체한다. 정본은 바꾸지 않는다.
- 실패(참조 사진 누락·해시 불일치, 사본 작성 실패, 검증 실패, SQLite 오류)는 이전 백업·포인터를 그대로 두고 부분 산출물을 `failed-<run8>/` 로 격리한다. 결과 문구가 이전 백업 버전·시각을 함께 알린다. `logs/backup.log` 에 한 줄 기록.
- `verify_backup_dir`: manifest 스키마, 파일 목록·크기·해시(누락·여분 없음), DB 사본 무결성·외래키·행 수·meta, 정본 사본이 참조한 사진 전부가 목록에 같은 해시로 있음(사진 연결), 목록의 사진이 전부 참조됨.
- `restore_backup(backup_dir, dest_home)`: 빈 폴더(이전 복구 시도의 `logs/` 만 허용)에만 한다. 백업 전체 검증 → `.restoring-<run8>/` 스테이징에 해시 재검증 복사 → 스테이징의 정본을 `Db.open` 으로 열어(외래키·마이그레이션) 행 수·버전·study_id·data_mode·사진 연결 확인 → `db/`·`photos/` 를 제자리로 → 최종 확인 → `logs/restore.log`. 실패하면 스테이징(백업의 사본)만 지우고 백업 원본·대상은 그대로다.
- `backup_status`: 정본 버전 vs 포인터의 백업 버전, manifest 파일 존재·해시를 실제로 확인해 `최신 / 백업 필요 / 없음 / 손상 / 접근 불가(외장 드라이브 미연결)` 를 판단한다. `j5 db status` 가 표시하며, data_home 없이는 `파일 미확인`.
- `check_photos`(사진 대사): 정본 attachments 가 참조한 파일의 존재·크기·해시와 `photos/` 의 미참조 파일. 아무것도 지우지 않는다. CLI `j5 db check-photos`, 종료 코드 0/1.
- `Db.snapshot()`: 읽기 트랜잭션. 안에서 `transaction()` 은 거절(`snapshot_read_only`), 쓰기 트랜잭션 안에서 여는 것도 거절(`in_transaction`: 같은 연결의 쓰기 잠금 안에서는 백업 API 가 진행되지 않음을 확인해 거절로 처리).
- CLI `j5 db backup [--dest] [--json]`, `backup-verify <dir>`, `restore <dir> <dest>`, `check-photos`. 종료 코드 0 완료 / 1 실패 / 3 사용 오류.
- `schemas/backup_manifest.schema.json`, 테스트 `tests/test_j5_012_backup.py` 14건(위 항목 + CLI + 리뷰 반영 3건). 전체 pytest 184건 통과.

## 데이터 사전에 없어 정한 값

- 백업 폴더 `J5_DATA_HOME/backups/<YYYYMMDD-HHMMSS>-ds<버전>-<run8>/` 안에 `backup_manifest.json`·`db/j5.sqlite3`·`photos/<sha 앞 2자>/<sha>.<ext>`(정본과 같은 상대경로). 포인터 `backups/latest.json`(run_id·created_at·dataset_version·db_schema_version·dir·manifest_sha256). `--dest` 로 다른 상위 폴더에 두면 포인터의 `dir` 은 절대경로다.
- 백업 대상은 정본 파일과 첨부가 참조한 사진뿐이다. 파생본(재생성 가능)·입력 패키지(원본 보관은 별도)·로그는 넣지 않는다.
- 참조 사진이 하나라도 없거나 다르면 백업 실패다. 사진 없는 DB 사본을 완전한 백업으로 표시하지 않는다. 사진을 이전 백업에서 되찾은 뒤 다시 백업한다.
- 백업 기록은 정본에 두지 않는다(정본을 바꾸지 않으려고). 상태는 포인터·파일·로그로 판단하며, 그래서 data_home 없이는 미확인이다.
- 복구는 빈 폴더에만 한다. 기존 정본을 덮어쓰는 복구 명령은 두지 않는다(필요하면 사용자가 폴더를 옮기고 복구한다).
- 오래된 백업·`failed-*`·미참조 사진은 자동 삭제하지 않는다. 정리는 사용자가 목록을 보고 한다.
- `--dest` 가 정본과 같은 장치면 결과에 주의를 표시한다. 독립 위치 여부는 사용자가 판단한다. 암호화는 하지 않는다(§12: 검증된 도구·기기 기능을 쓴다).

## 공수

- 예상 6~10시간. 실제(세션 기준) 약 1시간. 재작업: 같은 연결의 쓰기 트랜잭션 안에서 `Connection.backup()` 이 멈추는 것을 확인하고 읽기 스냅샷 방식으로 바꿈; 지연 트랜잭션이 첫 읽기 전에는 잠금을 잡지 않아 스냅샷 시작 시 읽기 한 번을 넣음; 실패한 복구가 남긴 `logs/` 때문에 재시도가 막히던 것을 `logs/` 만 허용으로 조정.

- 리뷰 반영(PR #38, Codex 3건): 복구 대조를 마이그레이션 적용 전(파일 그대로, 읽기 전용)과 후(데이터 테이블만, `schema_migrations` 는 이상)로 나눠 도구가 백업보다 새로워도 복구되게 함; 실패 처리 중 손상된 `latest.json` 을 안전하게 읽어 결과 객체로 끝냄; 상태 표시가 포인터의 study_id·data_mode 를 열린 정본과 대조해 다른 정본의 백업을 '최신' 이라 하지 않음.

## 미확인 변수·남은 인수조건

- "실제 두 차례 임장 후 사용성 결함 수정·일반 운영 전환"(릴리스 계획 §5)은 실기기·실사용 항목이라 이 PR 에 없다. 실사용 뒤 별도 작업으로 기록한다.
- 미뤄둔 실기기 시험(J5-004·006·007·지도)도 그대로 남아 있다.
- 외장 드라이브·다른 장치의 실제 fsync·rename 동작(특히 exFAT·네트워크 드라이브)은 검증하지 않았다. 백업 후 `backup-verify` 로 확인한다.
- 사진이 많아지면 백업이 매번 전량 복사한다(증분 없음). 실제 부담을 기록한 뒤 R6 에서 재검토한다.
