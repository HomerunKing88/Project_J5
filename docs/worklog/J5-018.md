# J5-018 매입 준비 UI·조건 갱신 (R7)

기록일: 2026-09-26. 첫 조각 **A**: 매입 준비 검토 기록 종류와 진입조건 판정·본인 승인·철회(PC CLI). 완료 조건 "유효한 근거·본인 승인·변경 시 재검토"(릴리스 계획 §10), §9 R7 인수 "만료된 은행 검토, 미확인 보증금 명세, 바뀐 매입 범위, 미해결 명도 조건이 남으면 준비 완료가 되지 않는다. 중요한 입력이 변경되면 영향받은 검토를 다시 요구하고 과거 승인 이력을 보존한다", 데이터 사전 §11, ADR-07. 계약 전·잔금 전 재확인과 비교자료 내보내기는 뒤 조각이다.

## A. 결과

- db_schema 13 `r7_acquisition_review`: `records.record_type` 에 `acquisition_review` 를 허용하는 표 재작성(마이그레이션 9·12 와 같은 절차, ADR-14; 마이그레이션 12 의 목록은 `RECORD_TYPES_V12` 로 고정)과 `readiness_decisions`(불변, 갱신·삭제 트리거 거절: 물건·검토 기록·결정 approve/withdraw·결정일·이전/새 관심 단계·사유·판정 스냅샷·정본 반영 시각). 승인이면 새 상태가 purchase_ready 여야 한다(CHECK).
- 입력 계약 `schemas/acquisition_review.schema.json`(`kind: acquisition_review`, 자료 종류 `personal_estimate` 고정): 전략, 범위(전체/지분/구분소유, 지분이면 비율, 필지 PNU, 건물, 구성 기준일), 가격(계약 총액은 보증금 차감 전 ADR-08, 미확인은 null 과 사유, 보증금 총액과 근거, 부가세 포함 여부, 호가 확인 수준), 참조 기록 5종(null 허용), 매물 사건, 체크리스트 버전 1.0.0, 체크 8항목(데이터 사전 §11 표의 8행: 매입 범위·가격 / 금융 / 세무·법적 검토 / 권리·임대차 / 건축·토지 / 사업·자금 / 계약 협상 / 최종 의사결정) 각 1회. 항목 필드는 §11 그대로(`status, evidence_ids, reviewer_role, checked_at, valid_until?, recheck_triggers, open_issues, not_applicable_reason`). 스키마 조건: `verified` 는 검토일 필수, `not_applicable` 은 사유 필수, `conditional`·`blocked` 는 미해결 사항 1건 이상. 코드 검사: 유효기한이 검토일보다 앞서면 거절, 항목 검토일이 기록 검토일보다 뒤면 거절.
- `j5 db case-add`(`j5/db/readiness.py`): 물건·근거 문서(기록 근거와 항목 근거 모두 `source_documents`)·참조 기록(같은 물건의 해당 종류이고 수정되지 않은 기록)을 대조하고 불변 기록으로 넣는다. 물건마다 현재(수정되지 않은) 검토는 하나: 현재 검토가 있는데 `supersedes_id` 없이 넣으면 거절. 관심 단계는 바꾸지 않는다.
- `j5 db readiness --asset [--as-of]`: 판정만 한다. 항목 verdict: `ok`(verified 이고 유효기한 안), `not_applicable`, `expired`(유효기한 < 기준일), `incomplete`(미착수·진행 중), `conditional`, `blocked`, `recheck`(검토 뒤 변경 중 그 항목의 재검토 조건에 해당하는 것이 있음). 중요 미확인: 계약 총액·보증금 명세·부가세·호가 확인 수준, 목표 매수가 없음, 자금안 없음, 참조 자금안의 필요자기자본·최대 필요자기자본 미확정, 참조 개발안(현상 유지 제외)의 여유면적 미확정, 참조 규제 검토가 가정값·효력 미확인·종료일 미확인, 참조 기록이 정본에 없음. 변경 신호(검토 기록의 정본 반영 시각 뒤): 새 목표 매수가=`price`, 새 자금안=`loan`, 새 개발안=`strategy`, 새 규제 검토=`regulation`, `asset_components` 갱신=`composition`, 변화 확인 관측=`due_diligence`, 참조 기록이 수정됨=참조 종류별 변경(목표가→가격, 투자판단→전략, 자금안→대출·보증금, 개발안→전략, 규제→규제). 준비 완료 = 모든 항목 ok 또는 not_applicable 이고 미확인·차단 사유가 없음. `release_required` = purchase_ready 인데 준비가 아니거나 승인 뒤 변경이 있거나 승인한 검토 기록이 현재 기록이 아님. 종료 코드 0 준비 완료(해제 필요 없음) / 1.
- `j5 db readiness-approve --asset --on [--note]`: 준비 완료일 때만. 이미 purchase_ready, excluded/archived 는 거절. `assets.tracking_status` 를 purchase_ready 로 바꾸고 결정 행(판정 스냅샷 포함)을 남기며 dataset_version 을 올린다. `readiness-withdraw --asset --on --reason`: purchase_ready 일 때만, 사유 필수, 관심 단계를 `detailed_review` 로 되돌린다. 승인 이력은 남는다. 재전환은 변경을 반영한 새 검토 기록 + 승인.
- 리뷰 반영(PR #60, Codex 4건): (1) `verified` 항목은 근거 문서 1건 이상이 있어야 한다(스키마 `minItems`, 판정에서도 근거 없는 확인은 미완료). (2) 항목별 최소 재검토 조건 `MANDATORY_TRIGGERS` 를 도구가 정하고 입력의 `recheck_triggers` 는 더할 수만 있다(빈 조건으로 변경을 피할 수 없다). (3) 구성 변경은 같은 초의 `updated_at` 도 검토 뒤로 본다(안전한 쪽). (4) 유효하지 않은 purchase_ready 는 `readiness` 명령과 파생본 생성(`db project`)이 `[자동 해제]` 사유·판정 스냅샷과 함께 자동 철회한다(`enforce_release`/`enforce_all`). 게시본의 관심 단계는 오래된 purchase_ready 를 담지 않는다.
- 테스트 `tests/test_j5_018a_readiness.py` 6건: 버전 12 정본을 열 때 표 재작성·보존·결정 표, 입력 검증 12가지, 판정 흐름(미완료·미확인 보증금·자금안 없음 → 만료(기준일에 따라) → 조건부 명도 → 미확정 자금안 → 준비 → 승인 → 새 자금안으로 재검토·해제 필요 → 목표가 수정 → 철회·복귀·이력 2건·불변 → 새 검토로 재승인), 구성 변경·관측 변경 신호, CLI. `tests/test_j5_009_db.py` 종류 행렬에 새 종류 추가.

## 데이터 사전에 없어 정한 값

- 체크리스트 8항목은 모두 필수 항목이다(§11 표의 8행). "필수 항목이 verified 또는 사유 있는 not_applicable" 을 그대로 쓰며 선택 항목을 따로 두지 않는다. 항목을 더 쪼개려면 체크리스트 버전을 올린다.
- 자료 종류는 `personal_estimate` 고정이다. 검토는 소유자 본인의 판단이고 근거는 항목별 `evidence_ids`(정본 문서)로 잇는다.
- 재검토 조건은 8종 enum(가격·대출·임대보증금·전략·구성 토지·규제·중요 실사 결과·임대차)이다. 항목별 최소 조건은 도구가 정한다(`MANDATORY_TRIGGERS`: 예 금융=대출·보증금·가격, 권리·임대차=임대차·보증금·실사·구성, 최종 의사결정=8종 전부). 입력의 `recheck_triggers` 는 더할 수만 있다. 해당 없음 항목도 조건에 걸리면 재검토다(해당 여부가 바뀔 수 있다).
- 변경 감지는 정본 반영 시각(`recorded_at`, `updated_at`) 기준이다. 검토할 때 이미 반영된 정보는 변경이 아니다. 거래 연결·취소·범위 규칙 변경은 목표 매수가 재확인(`db recheck`)이 맡고 여기서는 신호로 쓰지 않는다(목표가가 바뀌면 새 목표가 기록이 `price` 변경으로 잡힌다).
- 해제는 자동이다(데이터 사전 §11 "영향을 받는 체크를 재검토 상태로 바꾸고 purchase_ready 를 해제한다"). 판정 함수(`evaluate`)는 읽기 전용이고, `readiness` 명령과 파생본 생성이 `enforce_release`/`enforce_all` 로 유효하지 않은 purchase_ready 를 `[자동 해제] <사유>` 결정으로 철회한다. 변경을 넣는 명령(plan-add 등)은 그 자체로 상태를 바꾸지 않으므로 변경 뒤에는 `readiness` 또는 `project` 를 돌린다. 수동 철회(`readiness-withdraw`)는 새 위험을 사람이 확인했을 때 쓴다.
- 철회 뒤 관심 단계는 `detailed_review` 다(승인 전 단계가 unreviewed 였더라도). 준비 검토를 한 물건은 상세 검토 중인 물건이다.
- 판정 스냅샷(`evaluation_json`)은 결정 시점의 항목 verdict·미확인·신호·차단 사유를 담는다. 나중에 판정 규칙이 바뀌어도 결정 당시 근거가 남는다.

## 공수

- 예상(J5-018 전체): 릴리스 계획 R7 예산 범위. A 실제 약 2.5시간(리뷰 반영 포함).

## 미확인 변수·남은 인수조건

- 실제 물건의 체크리스트 운용(전문가 검토 결과·유효기한 입력)은 실사용 항목이다. 금융기관 사전 한도의 유효기한은 은행 회신 문서 기준으로 사용자가 넣는다.
- 남은 R7 항목: 계약 직전·잔금 직전 재확인(권리·규제·임대차 재점검 기록), 비교자료 내보내기(매입 검토 사건의 범위·가격·전략·금융·임대차·규제·실사·협상안 묶음 CSV/JSON), 폰 화면 표시(현재 관심 단계·준비 여부는 PC 판정이므로 파생본 시드에 tracking_status 가 이미 들어간다. 별도 화면은 필요가 확인되면 둔다).
