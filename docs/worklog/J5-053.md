# J5-053 폰 연도별 요약의 소유 변동일

기록일: 2026-10-02. PC `db parcels-years`(J5-045)는 연도마다 그 연도의 소유 변동일을 적지만, 폰 필지 이력의 연도별 요약(J5-047)에는 이 칸이 없었다. 폰은 필지 패널의 현재 소유구분 옆에 변동일 하나만 보였고, 이전 기준일의 변동일은 이력 항목을 하나씩 열어야 보였다.

## 결과

- `web/app/parcels.js` `ownershipChanges(attrs, history)`: 파생본의 현재 속성과 토지소유 변화 항목(이전 값과 새 값)에 적힌 소유 변동일(YYYY-MM-DD, 오름차순, 중복 없음)과 토지소유 자료 여부 `known`. 변화 항목은 이전 값과 새 값을 함께 담으므로 기준일마다의 값이 모두 모인다. 소유자 정보는 담지 않는다.
- `web/app/view.js` `parcelYearSummaryInfo(…, { ownership })`: 줄마다 `owner = { known, dates }`(그 연도의 날짜). 소유 변동일은 오래된 날짜가 많아 연도 범위를 넓히는 데 쓰지 않는다(PC 와 같다). `yearSummaryRow` 가 " · 소유 변동 날짜" 또는 자료가 없으면 " · 소유 자료 없음" 을 덧붙인다(PC `years_text` 와 같은 글).
- `web/app/main.js`: 필지 이력을 열 때 `ownershipChanges` 결과를 넘긴다. 앱 0.2.20(`APP_VERSION`, `sw.js` 캐시, e2e 2곳).
- PC `j5/db/parcel_years.py`: `ownership_snapshot` 을 "값이 하나라도 든 토지소유 스냅샷이 있다" 로 고쳤다. 원본에 소유 행이 없는 필지는 스냅샷 값이 모두 null 인데, 이전에는 자료가 있는 것으로 보아 변동일 빈 칸이 "변동 없음" 으로 읽혔다. 폰과 같은 규칙이다.
- 시험
  - `tests/web/parcels.test.mjs`: `ownershipChanges`(이전·새 값 모으기, 현재 값만, 값이 모두 null 이면 모름, 날짜 형식 아님, 입력 없음).
  - `tests/web/view.test.mjs`: 연도별 요약의 소유 변동일·범위를 넓히지 않음·소유 자료 없음 글·주지 않으면 칸 없음.
  - `tests/test_j5_053_phone_ownership.py`: PC 의 값이 모두 null 인 스냅샷은 자료 없음, 같은 가상 파생본으로 폰(Node 실행)과 PC 의 변동일·자료 여부가 같음.
  - `tests/web/app.e2e.test.mjs`: 가상 파생본 필지 1 의 2026 줄에 "소유 변동 2026-09-24".
  - 새 시험은 고치기 전 코드에서 실패함을 확인했다.
- 리뷰 반영(PR #100): 폰 연도별 요약의 끝 연도를 PC 처럼 "올해" 까지 늘린다. 폰의 올해는 PC 자료 파일을 만든 해(manifest `generated_at`)이고 기기 시계를 쓰지 않는다. 공시지가·거래가 지난해까지여도 올해의 소유 변동이 보인다. 시험 파생본(`tests/fixtures/make_view.py`)의 생성 시각을 고정해 해가 바뀌어도 e2e 가 같다.
- 별도 커밋: `tests/test_j5_015a_judgment.py` 의 `record-add`·`asof` 시험이 실제 시계를 따라 2026-10-01 부터 main 에서도 실패했다(`--at 2026-09-30 --as-recorded` 는 그날까지 기록된 것만 본다). 시험 안에서 정본 시각을 고정했다. 코드 동작 변경은 없다.

## 데이터 사전에 없어 정한 값

- 토지소유 자료 여부: 현재 속성의 소유 필드 중 하나라도 값이 있거나 토지소유 변화 항목이 하나라도 있으면 있음. 정본에서는 값이 하나라도 든 토지소유 스냅샷이 있으면 있음. 두 규칙은 같은 결과를 낸다(변화 항목은 값이 생기거나 바뀔 때만 생긴다).
- 파생본 이력 상한(필지마다 200항목)으로 앞부분이 잘린 필지는 그보다 오래된 소유 변동일이 폰에서 빠질 수 있다. PC 표는 정본 전체를 본다.
