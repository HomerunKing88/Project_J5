# J5-041 대규모 가상 정본 실측과 파생본 생성 단축

기록일: 2026-09-28. J5-039(ADR-23)와 J5-040 으로 정본이 수만 필지를 담을 수 있게 됐다. 두 작업의 미확인 변수였던 "수만 필지에서의 실행 시간" 을 작업 환경에서 가상자료로 재고, 가장 큰 병목을 줄였다.

## 실측 (작업 환경 컨테이너, Python 3.11, 가상 정본)

- 자료: 가상 필지 30,000개(법정동 10개, 법정동당 3,000), 속성 포함, 물건 50개(위치점 있음). 8,000필지 번들 4개로 반영했다. 실측 스크립트와 정본은 저장소 밖 임시 폴더에 두고 확인 뒤 지웠다.
- 반영 결과: 30,000필지 반영 40.2초. 번들마다 JSON Schema 검증과 트랜잭션 반영이 들어간다.
- 조건 찾기와 폰 범위 요약:

  | 작업 | 시간 |
  |---|---|
  | `parcels-find --zone com` | 0.98초 |
  | `parcels-find --assets none` | 1.14초 (필지마다 물건 위치점 포함 검사) |
  | `phone-scope` 요약 | 0.03초 |
  | 범위 지정 | 0.02초 |

- 파생본 생성(폰 범위 2개 법정동, 6,000필지):
  - 고치기 전: 29.2초. 프로파일 결과 시간의 대부분(프로파일 모드 82초 중 74초)이 필지 번들 JSON Schema 검증이었다. 생성할 때 한 번, 쓴 파일을 다시 읽는 게시 전 확인에서 한 번, 모두 두 번 했다.
  - 고친 뒤: 18.7초.
  - 폰 상한을 넘는 범위(9,000필지)는 4.5초 만에 `parcels_phone_limit` 로 실패하고 안내한다.
- 가상자료 실측이며 실제 PC·실제 자료의 시간이 아니다. 실제 자료의 도형은 꼭짓점이 더 많아 검증·쓰기가 더 걸릴 수 있다.

## 결과

- `j5/db/projection.py`: 생성 단계의 필지 번들 스키마 검증을 뺐다. 게시 전 확인(`verify_projection_dir`)은 쓴 파일을 다시 읽어 검증하므로 안전성은 같다. 스키마 위반이면 오류 내용 앞 3개를 안내에 담는다(이전에는 생성 단계의 안내에만 있었다).
- 시험 `tests/test_j5_041_projection_verify.py` 1건: 스키마 위반 번들은 게시하지 않고 이전 파생본을 유지한다.
- 문서: 릴리스 계획 §10 J5-041, `tests/README.md`, 색인(J5-040 #87).

## 테스트 명령과 결과 (2026-09-28, 컨테이너 Linux, Node 22, Python 3.11)

- `python -m pytest -W error::UserWarning` → 410 passed (새 시험 1건 포함).

## 실제 작업 시간

약 0.5시간 (실측 스크립트·측정 0.2, 프로파일·수정 0.15, 시험·문서 0.15).

## 미확인 변수

- 번들 반영(`load_bundle`)도 번들마다 스키마를 검증한다(입력 파일 검사라 줄이지 않았다). 30,000필지에 40초는 한 번 넣는 작업으로 받아들일 만하다고 보지만 실제 PC 에서 잰다.
- 남은 파생본 생성 시간의 대부분은 한 번 남은 스키마 검증이다. 더 줄이려면 검증기를 바꿔야 하며, 스키마가 계약이라 이번에는 하지 않았다.

## 남은 인수조건·후속 작업

- 사용자(PC): 여러 지역을 넣은 뒤 `db project` 실행 시간을 기록한다.
